#+TITLE: The boundary
#+SUBTITLE: what belongs in Lisp, what belongs in Rust, and every known ceiling

* The rule

#+begin_quote
You should be able to do anything in Lisp, but also do performance-intensive
stuff in Rust.
#+end_quote

Which means the Lisp API is judged on *reach*, not on size: nothing about the
editor should be unreachable from the image. It is not judged on speed, because
the heavy lifting stays behind primitives.

Concretely:

| In Rust                                     | In Lisp                                    |
|---------------------------------------------+--------------------------------------------|
| The rope, and every edit to it               | Which edit to make, and when               |
| tree-sitter parsing and highlight spans      | What colour each highlight class is        |
| Highlighting *a string* as a named language  | Which strings, and what to do with the runs |
| Glyph rasterisation and the frame            | Font size, theme, modeline geometry        |
| The vim grammar: counts, operators, motions  | Every key binding on top of it             |
| Window layout arithmetic and hit-testing     | When to split, close, focus                |
| Characters to cells, and where a line wraps  | Nothing — there is no reader in cells      |
| Reading and writing files, git, ripgrep, PTYs | Which file, which verb, and what to do next |
| Mode *storage*: one name plus a list         | The whole mode *system*                     |
| A child process, JSON framing, JSON decoding | Every protocol spoken down it, LSP included |
| Walking a project's whole tree, and caching it | Every =project-= verb, and which files make a directory a project |
| Expanding the modeline's =%= codes, per frame  | What the modeline *says*, and in what order  |

The subprocess row is the newest and the same argument. =crates/rpc= spawns the
child, frames =Content-Length= messages, hands each decoded message to the image
as a *Lisp form*, and knows nothing about =initialize=, capabilities or
diagnostics — all of which live in =runtime/lsp.lisp=, where adding a third
language server is one line and no rebuild.

The mode row is the clearest case. Rust knows a buffer has a =major_mode= string
and a =minor_modes= list, and that entering a mode means "call =X-hook=". It knows
nothing about inheritance, exit hooks, mode-local settings, or picking a mode
from a filename — all of which are Lisp, in =runtime/modes/modes.lisp=, for
exactly the reason Emacs builds them in elisp rather than in C: *that is the part
every config wants to bend, and the image is where bending costs nothing.*

* How to decide where a new thing goes

In order. Stop at the first one that works.

1. *Can it be written as a Lisp function over what already exists?* Write it
   there. =switch-to-buffer=, =save-excursion=, =replace-all=, =where-is= and
   =buffer-lines= are all in this category, and none of them is a primitive.
2. *Is it a new question about editor state?* Add a reader: one arm of the
   =match= in =crates/core/src/query.rs= and one name in the list in =QUERIES_FORM=.
   Nothing in C. If answering it needs a crate that depends *on* core — a parse,
   a LaTeX scan — then =query.rs= cannot reach it and the arm goes in =ask_here=
   in =crates/lisp/src/lib.rs= instead, which is tried first and falls through.
   Same envelope, same spelling from Lisp; only the file differs.
3. *Is it a new command whose arguments fit "a verb, maybe a string, up to two
   integers"?* Add a verb: one arm of =command_for= in =crates/lisp/src/lib.rs= and
   a one-line =DEFUN= in =shim.c=. Nothing in C.
4. *Does it need a shape those two envelopes cannot carry* — floats going out, a
   handle coming back? Then it earns a C primitive. =set-background= (three
   floats) and =%make-marker= (a handle) are the two kinds.
5. *Is it hot enough that Lisp doing it per keystroke would be felt?* Then it is
   Rust, and Lisp gets a knob rather than a hook. Highlighting and layout are
   here.

The asymmetry is deliberate. Adding to Lisp costs a line. Adding a C primitive
costs a Rust function, an =extern=, a C wrapper, a =defprim= and an export — five
places that can drift out of step. A helper beats a primitive; composition beats
a new entry point.

* What is genuinely unreachable from Lisp

These are not oversights and not shortcuts: each needs a new =EditorCommand=
variant or a new accessor in =crates/core/src/lib.rs=, which is the one file the
Lisp side cannot work around.

| Missing                              | What is in the way                                                      |
|--------------------------------------+-------------------------------------------------------------------------|
| Interrupt a runaway form             | The Lisp thread evaluates one queued form at a time and nothing can preempt it. |
| Ask a question that *guards* a command | =PromptKind::Confirm= parks an =EditorCommand= in =Editor::pending_confirm= and runs it on a full =yes=. =read-string= is the Lisp prompt and it is a continuation with no command behind it, so a Lisp guard is a callback the caller can forget to write. See below. |

That table used to have eight rows. Seven of them were closed by *nine =%do=
verbs and two accessors* — no new C primitive, no new =defprim=, nothing in
=shim.c= except Lisp — which is the ladder above working exactly as intended:
what looked like "the Lisp API needs a way in" was, every time, one arm of
=command_for= and one arm of =Editor::apply=.

| Was missing                          | What closed it                                                          |
|--------------------------------------+-------------------------------------------------------------------------|
| Create a buffer with no file behind it | =(create-buffer name &optional language)=, verb ="create-buffer"=. Idempotent by name, applied on the spot, an *ordinary* buffer rather than a generated one. |
| Kill a buffer                        | =(kill-buffer &optional name)=, verb ="kill-buffer"=. The last one is refused; windows showing it follow the live buffer. |
| Get an answer back from the user     | =(read-string label callback)= and =(completing-read label candidates callback)=, verbs ="read-from-minibuffer"= and ="prompt-item"=. See below — it is a continuation, not a blocking read. |
| Send a keystroke to the shell        | =(term-send-key key)=, verb ="term-key"=, over =Key::from_token= — the inverse of the =Key::token= that =key-bindings= already reports. One vocabulary, both directions. |
| Run a built-in verb by name          | =(call-command name)=, verb ="call"=. =Editor::run_action= is public and answers a *batch*, so the verb is resolved in =rs_do= beside =paste= rather than in =command_for=. |
| Seed a prompt with text or candidates core owns | =(%do "prompt-text" …)=, =(%do "prompt-label" …)= and =(%do "prompt-source" "SOURCE ARGUMENT")=. The first two set fields; the third is the interesting one — Lisp *names* a list the app owns and the app pours it straight into the open prompt, so a repository's fifty thousand paths never become Lisp objects. This is what let every =project-= picker move to =runtime/plugins/project.lisp=; see the entry below. |
| Hand a long candidate list to =completing-read= | =(%do "prompt-items" …)=, one newline-joined string. It used to be one =%do= per candidate, which =shim.c= said outright was fine for a few hundred and wanted another route past that. |
| Say what the modeline says              | =(clear-modeline)= and =(modeline-segment SIDE TEMPLATE …)=, verbs ="modeline-clear"= and ="modeline-segment"=. A *format* rather than a callback — see below. |
| Group several edits into one undo step | *Nothing, deliberately.* See below. |

** The prompt continuation, and why it is not a blocking read

The valuable one, and the only one whose shape needed thinking about. Every
other =PromptKind= has its destination fixed in core — a file is opened, a
command is run — and this one hands the reply to a Lisp closure.

It could not be =(setf answer (read-string "Name: "))=. The Lisp thread evaluates
one queued form at a time, so a primitive that waited on a keystroke would stop
*the image* — every mode hook, every key bound to a Lisp command, every =M-x= —
until the question was answered. That is precisely the elisp behaviour
[[file:threading.org][threading.org]] exists to avoid, and paying it back here for one convenience would
undo the whole design.

So the answer arrives the way a JSON-RPC reply already does, on purpose rather
than as a second mechanism: the closure is parked in =*prompt-continuations*=
under an id, the id rides into core inside the command, and accepting *or
cancelling* the prompt makes core emit =CallLisp= of =(%prompt-reply ID ANSWER)= —
the one route core has to reach the image, and the same one a mode hook takes.
Cancelling replies =NIL= rather than staying silent, so a callback is always
called exactly once and a command can clean up in it.

The id exists for the same reason =rpc-request='s does: a stale reply is dropped
rather than delivered to whoever asked most recently.

** Grouping N edits into one undo step: closed by argument, not by a feature

This row is gone because the mechanism should not exist, not because it was
built.

Every mutating primitive checkpoints *inside itself*, so "begin an undo group"
means one of two things, and both are worse than the alternative:

- a flag that makes the mutators skip checkpointing until it is cleared — which
  is left set forever the first time a Lisp error escapes between =begin= and
  =end=, and an editor that has quietly stopped recording undo is a far worse
  failure than N undo steps;
- a nesting counter with the same failure mode plus =unwind-protect= discipline
  at every call site.

And it would not even buy what it looks like it buys. Grouping makes N edits
*undo* together; it does nothing about the gap between them, so a keystroke can
still land in the middle and be typed into a half-finished edit. The thing that
fixes both is already there: build the whole text in Lisp and apply it with one
=replace-region=, which is one lock, one undo step and no gap. =replace-all= in
the standard library is exactly this, and it is why =replace-region= exists next
to =delete-region= and =insert=.

The table in [[file:threading.org][threading.org]] is the documentation this row wanted.

** A destructive verb's guard cannot move to Lisp

The finding of wave 2, and the reason =crates/app/src/magit.rs= and
=crates/app/src/dired.rs= still hold their confirmation guards.

The guard's whole value is that it is a *funnel*: =r a=, =M-x magit-rebase-abort=
and =(magit "rebase-abort")= are three doors that arrive as one
=EditorCommand::Git=, so one check in =Magit::run= covers all three and the
person who adds a fourth door gets it for free. Move the check into a Lisp
=magit-rebase-abort= and the third door walks straight past it — =(magit
"rebase-abort")= is =%do "git"=, which is the command and not the name — so the
guard would have to be re-stated at every caller, which is the arrangement the
guard exists instead of.

The only shape that keeps the property is core *asking the image* on the way
through =EditorCommand::Git=, which means every git verb blocking on a Lisp
round trip. That is the one thing [[file:threading.org][threading.org]] promises never happens.

So: **a question that decides whether a command runs is Rust's**, and stays
beside the funnel it guards. A question whose answer is data — a filename, a
make target, a git URL — is =read-string= and belongs in Lisp. The two are not
the same feature and the second is not a step toward the first.

* Known ceilings that a config will actually feel

These are deliberate shortcuts, marked =ponytail:= in the source. Each names its
ceiling and its upgrade path where the source does.

** Half of =project.rs= is in Lisp and half is not — *closed*

Was: =runtime/plugins/project.lisp= owned =project-root=, =project-dired=,
=project-compile= and =project-test=, while =crates/app/src/project.rs= still
owned =project-find-file=, =project-find-dir=, =project-forget=,
=project-switch= and =project-open=. One feature, two files, and a real cost
when you are hunting for where a verb lives. The four that had not moved were a
walk of the whole tree behind a cache that has to answer between two keystrokes,
and two prompts that needed seeding with candidates core owns.

What landed is the three prompt verbs in the table above, and =prompt-source= is
the one that mattered. The naive close — a =project-files= *reader* — would have
carried tens of thousands of paths into the image as printed source for ECL to
parse, and then carried them straight back out again as candidates: two
crossings of the exact list the cache exists so that nobody walks twice. So Lisp
names the list instead. =(%do "prompt-source" "project-files /some/root")= and
the app fills the open prompt directly, while the label, the callback and *what
accepting one means* stay in the image, where a config can make =SPC p f= open in
the other window by changing one symbol.

=project-switch= went the other way and is the contrast worth keeping: the
projects visited before are a few dozen paths, so that one *is* a reader
(=project-recent=, an =ask_here= arm — the route =latex-fragments= and
=fold-ranges= take, plus the workspace edge this entry used to price). Having the
list in the image is what lets =project-switch= notice it is empty and hand over
to =project-open= rather than opening a picker onto nothing. **A list you only
show goes by name; a list you have to reason about comes across.**

What is left in =project.rs= is not a verb. =Cache= walks the tree,
=search_root= is where a project-scoped ripgrep starts, and =project-forget=
drops the cache — the one thing under =project-= with nothing in it for a config
to bend.

Two rules for the same tree still exist — =%project-at= in Lisp and
=zemacs_project::find= in Rust — but they no longer *decide* the same thing. Lisp
picks the root for every verb and hands it to the walk, so a disagreement can no
longer put the picker in a different tree from the one =SPC p r= reports; the
Rust climb survives only for =search_root=. =crates/lisp/tests/project_plugin.rs=
still pins the Lisp rule against the trees =crates/project/tests/project.rs=
builds for the Rust one.

** The modeline is a format, not a callback

=crates/core/src/modeline.rs= used to *be* the strip: a function that pushed a
pill, then two spaces, then the buffer name, then a dot if modified, in that
order and in those colours. Every line of it was policy and none of it was
reachable from a config.

It is now a list of templates =default-modeline= in =runtime/library.lisp= sets
with =modeline-segment=,
each a little string of =%= codes — =%m= the modal state, =%b= the buffer, =%l=
the line — and the editor expands them per pane per frame. Rule 5 of the ladder
above, exactly: the shape is Lisp's and costs nothing to change, the expansion is
a scan of a few dozen bytes in Rust, and no frame waits on the image.

A callback per frame was the other design and is the one Emacs has. It is also
why a slow =mode-line-format= in Emacs makes the whole editor feel slow, and
[[file:threading.org][threading.org]] is a document about never doing that.

The one thing a format cannot say is =if=, and it does not need to: **a segment
whose codes all expand to nothing is dropped whole**, so =" %P"= carries its own
leading space and leaves with it on a buffer that has no file behind it. A format
language with conditionals in it is a programming language written in strings,
and the image is right there.

Two ceilings, both marked =ponytail:= in the source. Which face each *mode* takes
— insert green, visual magenta — is still a table in Rust; a config can move the
pill, restyle it or delete it, but not recolour =INSERT=. And the codes are a
fixed vocabulary: a field nobody thought of is a new arm in =Fields::code=
rather than a Lisp function, which is the price of not calling Lisp per frame.

** The shim returns bytes, not characters — *closed*

Was: =crates/lisp/src/shim.c=, =f_query=. Query answers arrived as an ECL *base*
string, so buffer text was its UTF-8 bytes rather than its characters:
=(length (buffer-string))= counted bytes, =%byte-index= and =%char-index=
converted between the two counts, and =utf8-text= in =runtime/modes/modes.lisp=
decoded at each of the dozen places text left a buffer.

The upgrade path this entry named — "decode into an extended string in =f_query=,
worth doing when a config genuinely does arithmetic on non-ASCII text" — was
right about the change and wrong about the price. It could not be done alone.
The *other* door into the image is =zemacs_eval=, which also handed ECL a base
string, so ECL's reader parsed a form's source as Latin-1 and =(message "λ")=
from a keybinding reached the status line as =Î»= while the same form in a
=load=ed file was fine. Decode one door and not the other and eval'd source stops
being comparable with buffer text: =(search-forward "γ" 0)= answers NIL, and
answering NIL is what a search does when it finds nothing, so nothing reports it.

What landed: =utf8_string= in =shim.c= decodes every string arriving from Rust —
=f_query=, =f_highlight=, =f_json_quote=, =zemacs_eval= and =zemacs_load_init= —
and =dup_utf8= encodes every string going back, with its fast path narrowed from
"a base string" to "an ASCII base string" so that =(code-char 233)= is encoded
rather than copied. Above that, **Lisp holds characters**: =%byte-index= and
=%char-index= are gone with their callers, =search-forward= is a bare =search=,
=utf8-text= is gone with its callers, and =(length (buffer-string))= is
=(point-max)=. =crates/lisp/tests/utf8.rs= pins both doors and the search that
needs them to agree.

The one place in the image that still counts bytes is =lsp-path-uri= /
=lsp-uri-path=, because a percent-escape names a byte; they use ECL's own
=ext:string-to-octets=.

** Non-ASCII sent to a subprocess is encoded twice — *closed*

Was: =runtime/rpc.lisp=, =json-string=. Text crossed the shim *twice* on its way
to a JSON-RPC child and =dup_utf8= encoded it at each crossing, so a server was
told a non-ASCII file contained mojibake. Caught by pointing the LSP client at a
Rust file with an emoji in it: rust-analyzer reported the string literal's value
as =ÃÂ°ÃÂ…= and put every column after it on that line eighteen places out.

The repair was a =utf8-text= in =json-string= and a matching one on every string
=runtime/lsp.lisp= sent, two halves of which neither was sufficient. Both are
gone. Text crosses once and is encoded once, because the model above the shim is
characters — see the entry above, of which this was always a symptom rather than
a second bug.

** Visual lines reach core through one integer

=crates/render/src/lib.rs=, =Renderer::render=. Where a line wraps depends on the
font, the pane and the gutter, none of which core can see — so the renderer parks
=wrap_cols= on each =Window= and on the =Editor= every frame, exactly as it does
=viewport_lines=, and core does the row arithmetic itself over
=crates/core/src/display.rs=. That is the whole channel; there is no second one.

Two consequences a config will feel:

- =0= means "nothing has drawn this window yet", which every reader takes as *no
  wrapping*. A Lisp-only or headless =Editor= moves by buffer line.
- Core lays a line out *with* its overlays — *closed*. It used not to, so a
  =display= substitution (an org-modern bullet, a checkbox glyph, a shortened
  link) moved the renderer's columns and not core's, and =j= down such a line
  landed a character off. =substitute= now lives in =crates/core/src/display.rs=
  beside =expand_line=, and =display::line_cells= — text, then the overlays'
  =display= strings — is what both =Editor::line_cells= and the renderer ask.
  What a substitution costs is unchanged and is the point: every character of a
  hidden range shares the first column of what replaced it, so the cursor on
  =[=, on the space and on =]= of a substituted =[ ]= is drawn in one place.
  Offsets are untouched — =x= still deletes the character the buffer has.

  What is *not* closed is the image half, and it is now *columns only*: the cells
  a bitmap reserves are =ceil(width / cell_w)= and a cell's width in pixels is the
  renderer's alone, so =display_subs= skips an image-only overlay and core counts
  its source text. Upgrade path: park a cell width on the =Editor= beside
  =wrap_cols=. The image's *rows* were the other half of this and turned out not
  to need the channel at all — they never left =crates/render=; see "Inline
  images" below.

With an operator pending, =j= and =k= are still *buffer* lines: =dj= deletes two
whole lines, as in vim. Emacs' =evil-next-visual-line= is an exclusive motion and
would delete to the same column one row down.

** Switching buffers fires no hook — *closed*

Was: the editor reported a mode being *entered* and never a buffer being
*switched*, so settings claimed by a mode followed the last mode entered rather
than the buffer on screen. Two org buffers were fine; flipping between an org
buffer and a rust one was not, and the cost was not momentary — one visit to a
=.rs= file took the wrapping and the 80-column measure off every org and prose
buffer for the rest of the session. The upgrade path written here was "a hook on
the buffer switch — a line in core, not in Lisp".

That is what landed. =Editor::announce_buffer_switch= queues =buffer-switch-hook=
on =pending_hooks=, from the two places the live buffer can change:
=switch_buffer=, which =switch_buffer_id=, =create_buffer=, =show_named= and
=load= on an already-open file all funnel through, and =adopt_window=, which is
focus moving between the panes of a split. =runtime/modes/modes.lisp= answers it
in two lines, because =%effective-setting= already recomputed from the bottom up
and =minor-modes= already read from the live buffer: the only thing ever stale
was =*major-mode*=.

The division of labour is the part to keep. =%enter-major-mode= owns *entering* a
mode — the departing mode's exit hook, the bodies, the auto-mode dispatch.
=buffer-switch-hook= owns re-resolving the claims for a *switch* and does nothing
else, because a switch enters no mode: the buffer was already in the one it is
in and its body ran when it got there. Running the bodies here would fire
=org-mode-exit-hook= every time you glanced at another file. The two never fire
for the same event — every route that swaps the live buffer queues no mode hook,
and every route that changes a buffer's mode swaps no buffer.

What is left is the one underneath, and it is the real one: these settings are
still **global in the editor**, one =line-overflow= for the whole application. A
split showing an org buffer beside a rust one can only be right about the pane
that has focus. Making them per-buffer is a change to =Settings= and to every
=EditorCommand= that writes one, and it would delete the claim machinery in
=modes.lisp= rather than extend it.

** The settings baseline starts at the factory default

=runtime/modes/modes.lisp=, =%wrap-setting-primitives=. The mode system wraps each
setting primitive to record what a config asked for. A setting changed *before*
=modes.lisp= is loaded is not seen, so load it above your appearance settings.

This one is now half-closed: every setting has a reader (=(font-size)=,
=(tab-width)=, =(line-overflow)= …), so the baseline could be read rather than
assumed. That change belongs in =modes.lisp=.

** A change notification carries no delta — *closed*

Was: the editor reported =after-change-hook= when the document's revision moved
and only *that* it moved, so Lisp had to read the buffer back to find out what
happened. The upgrade path written here was "core recording =(start, old-end,
new-end)= per edit and handing it to the hook".

That is what landed. =Change= is the record, =Buffer::changes_since= is the
reader, and =after_edit_form= in =crates/app/src/main.rs= delivers
=(after-edit-hook START OLD-END NEW-END TEXT)=. The text is sliced under the same
lock that produced the record, which is the load-bearing part: the image
evaluates the form a turn or more later, and offsets alone would name a document
that has since moved on.

What was left was one consumer's work, and =runtime/lsp.lisp= has now done it —
but *not* with this. It keeps the shadow copy per open file that this entry
predicted, and diffs it against the buffer to build the =contentChanges= range.
The delta hook it was built for is deliberately unused, and the reason is a
second ceiling this entry did not see: **the record names no buffer.** The image
evaluates the form a turn or more later, so a delta produced while you were in
one file arrives while you are in another, and =(buffer-file-name)= read in the
hook is as late as the hook is. There is no way in Lisp to tell, and applying one
document's delta to another's shadow is exactly the silent desynchronisation the
paragraph above exists to prevent — so the client reads the buffer instead, which
is current by construction.

Upgrade path, and it is small: the buffer's path as a fifth argument in
=after_edit_form=. With it the hook is usable and the read goes away; without it
the read is the price of being sure.

=point-moved-hook=, added beside it, still has the smaller version of the
original ceiling: it says point moved and not where it moved *from*. A config
that wants to act on the range you just left — re-typesetting the equation you
stepped out of — keeps the old position in a variable. It did not close with the
other half because the two travel differently: =pending_hooks= carries a name and
no arguments, where =after-edit-hook= gets its payload by being *formatted into
the form the app queues*. That route is open to any hook willing to pay for it.

** LSP columns are characters, not UTF-16 code units — *closed*

Was: =runtime/lsp.lisp= sent =(column)= where LSP wants a count of UTF-16 code
units, so a jump landed a column or two off. Two corrections to what this entry
used to say, because both sent you looking in the wrong place:

- The example was wrong. Characters and code units agree across the whole BMP,
  so an accent never moved a column. What moves one is a character *outside* the
  BMP — an emoji is one character and a surrogate *pair*. Measured against
  rust-analyzer: three emoji in a string literal put every position later on that
  line three columns out, and =g d= on the call after them asked about the local
  variable instead and jumped to it.
- The upgrade path was the wrong half. A reader in =query.rs= can only answer
  about the *live* buffer, and a =didChange= range is a position in the document
  the **server** has, which core cannot see. So the conversion is in Lisp, where
  both the buffer's line and the shadow copy are in reach, and there is one of it
  rather than two that can disagree.

What landed: =%lsp-utf16-column= and =%lsp-char-column= in =runtime/lsp.lisp=,
used in both directions — outgoing for =definition= and =completion= and for
every =didChange= range, incoming for a diagnostic's column, which is measured
against the shadow copy because a workspace analyser publishes for files that are
not on screen. Negotiating =positionEncoding= is still refused, and now for a
better reason than "not done": the only other spelling every server offers is
=utf-8=, which in LSP means *bytes*.

** Buffers are matched by name

=crates/lisp/src/shim.c=, =with-current-buffer=. Two files with the same base name
are indistinguishable and the first wins. Upgrade path: a reader keyed by buffer
id, which needs the ids exposed first.

=create-buffer= and =kill-buffer= are matched the same way and inherit the same
ceiling — which is also what makes =(create-buffer "*Messages*")= idempotent, so
here it is the feature rather than the shortcut.

** A Lisp prompt left open by another prompt

=crates/lisp/src/shim.c=, =PROMPT_FORM=. A =read-string= is answered on accept
*and* on cancel, so its continuation is always called — unless Lisp opens a
second prompt over the top of the first, which replaces the =Prompt= core is
holding and strands the closure in =*prompt-continuations*=.

A few conses, and only reachable from a config that puts a picker up from inside
a =read-string= rather than from its callback. =(clrhash *prompt-continuations*)=
is the sweep; the upgrade path is core replying =NIL= to the prompt it is about
to discard, which is three lines in =open_prompt=.

** =interactive= dispatches on "no arguments", not on how it was called

=runtime/library.lisp=, =%interactive=. Emacs asks a command for its arguments when
it is reached by =call-interactively= and not when it is =funcall=ed; here the two
are indistinguishable, because everything — =M-x=, a key binding, a dashboard item
— arrives in the image as the same bare =(name)=. So the wrapper asks when it was
given *no arguments at all*, which is a one-bit approximation of the same thing.

It costs a declared command that means something with none of its arguments.
=(set-language)= meant "plain text" and now asks; that call is spelled
=(set-language nil)=, an explicit =NIL= being an argument. Nothing else in the tree
relied on the distinction, and no command in the shipped runtime both takes
arguments and does something useful without them.

The upgrade path is a second entry point rather than a change of shape — core
sending =(%call-interactively "name")= for the =M-x= route while a key binding goes
on sending =(name)=. That was considered and rejected for now: it makes every key
bound to a Lisp command depend on a function defined in =library.lisp=, which the
mode tests and any config that stopped early on an error do not have.

** Arguments cannot be typed on the =M-x= line

=crates/core/src/minibuffer.rs=, =Prompt::submitted=. =M-x= candidates carry a
docstring and a key padded onto the row — =%annotated-command= in
=runtime/modes/which-key.lisp= — and core takes the *first word* of the accepted
row as the command name. An argument and an annotation are the same thing to it,
so =M-x set-scale 20= runs =set-scale= and throws the =20= away with the docstring.

The arguments are asked for in a prompt of their own instead, which is what
Emacs does too. Recovering the inline form would mean core deciding where the
annotation starts, or a Lisp reader on the Rust side of the boundary — and
neither buys anything the second prompt does not already give.

** A buffer Lisp made is not read-only — *closed*

Was: =BufferKind::is_generated= was the only thing that made a buffer refuse an
edit, so a buffer Lisp created (=*Messages*=, a =*xref*= listing) could be typed
into and the typing thrown away the next time the command regenerated it. The
upgrade path written here was "a per-buffer read-only flag rather than a kind,
which is what Emacs has".

That is what landed. =Buffer::read_only= is the flag, =(set-buffer-read-only)= is
the writer, and =Editor::apply= asks =Buffer::read_only()= — which answers
=ReadOnly::{No,Generated,Claimed}= — instead of asking the kind. The two reasons
stay apart because they behave differently: nothing can make a *generated*
buffer writable, and a *claimed* one is lifted for the duration of a
=with-inhibited-read-only=. =org-frozen-mode= is the first customer;
=(buffer-read-only-p)= reports which of the two it is.

What is still open is one line down from this: a buffer Lisp made is writable
*by default*, and a command that regenerates one has to claim the flag itself.
That is now a line of Lisp rather than a hole in the boundary.

** Markers

- =crates/core/src/lib.rs=, =step_history=: *closed.* Undo used to restore a whole
  snapshot and then clamp the markers into it, so one beyond the restored end
  landed on the end and one merely *pushed along* by the undone edit stayed
  pushed. It now diffs the two ropes — common prefix, common suffix, one
  contiguous range between, which is what a single undone edit differs by — and
  splices it, so markers and overlays run backwards through the edit the way
  they run forwards through an ordinary one.

  What that was costing was not markers. A LaTeX preview is an *overlay* over
  its fragment, and an undo anywhere above one left the image at its old offset
  while the text slid out from under it — reported as "previews mess up undo".
  Every fold, diagnostic mark and org-modern bullet had the same bug. The
  change record is now the range rather than =0..old -> 0..new=, so a =u= on one
  character is an incremental reparse and a small =didChange= as well.
- =crates/lisp/src/shim.c=: =(make-marker)= puts one *at point* rather than
  nowhere, and the insertion type is fixed at creation — there is no
  =set-marker-insertion-type=.
- =crates/core/src/marker.rs=: markers are a =Vec= scanned linearly, which is right
  for a few per buffer and wrong for one per hit of a search.

** Overlays

- =crates/core/src/overlay.rs=: an overlay's colours are *face names* from
  =face-list=, never an =(R G B)=. That is what keeps every overlay writer inside
  the =%do= envelope and out of C, and what makes an overlay follow =load-theme= for
  free. An overlay wanting a colour no face has must =set-syntax-color= a spare
  face first; the upgrade path is a primitive taking three floats, the shape
  =set-background= already has.
- The insertion types are fixed at Emacs' defaults — text typed at the front
  lands inside, text typed at the back lands outside — so there is no
  =front-advance= / =rear-advance=.
- An overlay whose text is entirely deleted is deleted with it, where Emacs would
  keep a zero-width one. Every payload here is *about* the text underneath, and a
  =display= string over no text is a ghost.
- =crates/lisp/src/shim.c=: the property list lives in the image, keyed by handle.
  =delete-overlay= and =remove-overlays= prune what they remove, but an overlay the
  *editor* deleted — because an edit swallowed its text — leaves a few conses
  behind. The comment above =OVERLAY_FORM= has the one-line sweep.
- =crates/core/src/overlay.rs=: the live set is a =Vec= scanned linearly, and the
  renderer walks the whole of it *per drawn line* — five times, for the display
  substitutions, the line style, the runs and the two fold questions. **Measured**
  at 45 drawn lines: one scan costs =0.03 ms= per frame at 24 overlays, =0.09 ms= at
  1024, =0.33 ms= at 4096 and =1.19 ms= at 16384 — flat noise until about a
  thousand and then linear at ≈7×10⁻⁵ ms per overlay per frame per scan. So the
  whole of a frame's overlay work is under a hundredth of a millisecond for the
  two dozen avy puts up, and the =Vec= becomes a real cost somewhere past ten
  thousand. This was the ceiling avy was expected to hit and it does not: it is
  capped at =(length *avy-keys*)= labels over the *visible* region, because an
  unlabelled candidate is not a candidate. Something that puts an overlay on
  every hit in a whole *buffer* would still hit it, and the answer is what it
  always was — keep the list sorted by =start= so a line can be binary-searched,
  or an interval tree.
- =fold= is the one property that is about *lines*: it makes the lines after the
  overlay's first stop occupying rows. Two-state only — a fold is closed or open,
  and opening one opens every fold inside it, which is org's =SUBTREE= and never
  its =CHILDREN=. Folding is per *buffer line*, so half a line cannot be hidden;
  the head line is always drawn, and there is no way to fold from the very top of
  a buffer with nothing above the region.
- =help-echo= is the one property that draws *nothing*: it is what the pointer
  resting on the overlay says, and the only reason it crosses into Rust at all is
  that the pointer is over there. It is read **through the gutter and nowhere
  else** — hovering the *text* a =help-echo= overlay covers answers nothing today.
  That is not an oversight about the mouse; it is honest about the overlays we
  actually make. A diagnostic's overlay deliberately spans its whole *line*, so
  that it slides with edits and can carry the gutter mark, which means a text hit
  test would fire on every column of every marked line as the pointer crossed the
  buffer. The upgrade path is a *second* overlay on the error's own range —
  =lsp.lisp='s to make, not core's — at which point the hit test is
  =click_target= plus the same =help_echo_at=, about four lines.
- The hit strip is the gutter's columns plus one =PAD=, so a buffer with a
  =text-width= does not answer for a pointer out in its centring margin. And
  =Renderer::gutter_row= asks the same =gutter_w= the draw loop asks before
  painting a mark, so "a mark is drawn here" and "something is hoverable here" are
  one question — including where the gutter is on for a reason nobody expected.
- One message per line, last overlay wins, exactly as the gutter *glyph* already
  resolves. Four diagnostics on one line — which is what =pylsp= sends for one bad
  import, from =mypy= and =ruff= at once — show the newest. Joining them is
  =lsp-diagnostics-at-point='s trick and belongs on the Lisp side, since "these two
  overlays are about the same complaint" is not a fact core has.
- The hover box itself is =Editor::tooltip=, in *pixels*, which core otherwise
  never deals in — the same exception =ContextMenu= and =Frame::divider_at= already
  are, and for the same reason: it is anchored to the pointer and not to anything
  in the document, so there is no offset for the renderer to convert. It is
  emptied in four places (a keystroke, a click, the wheel, the pointer leaving the
  window) and there is no fifth: nothing about the editor can answer "is the
  pointer still on the mark", so unlike =Editor::completion= this cannot be a
  predicate.

** Folding does not follow the scroll position exactly

=crates/render/src/lib.rs=, =visible_lines=. A folded line counts as a *line* and
costs no *row*, which is what lets =scroll= step over a fold — but the pane's row
budget is checked before each line is charged, so a run of folds at the very
bottom of the count is not reached. =viewport_lines= then under-reports slightly,
which lets the view scroll one screen further than it strictly needs to. That is
the safe direction; the other one would make the end of the file unreachable.

=Window::scroll= is still a *buffer line*, so scrolling to a line that is folded
lands the pane on the first drawn line after it. Upgrade path is the same one
wrapped lines want: a scroll position of (line, row).

=scroll-past-end= inherits exactly that and nothing more. Its limit is
=Editor::max_scroll=, and it is =buffer.last_line()= — the last line on the *top*
row rather than on the bottom one — which is a count of *lines* and therefore
needs no row arithmetic at all, so there is no second row-counting rule to
disagree with =visible_lines=. What it inherits is the fold: a fold covering the
end of the file can be scrolled into and draws an empty pane, which the old
clamp could already do one screenful earlier.

** Scrolling past the end of the document

=crates/core/src/lib.rs=, =Editor::max_scroll=. On by default, because both
editors this one is measured against do it and neither offers a way not to: vim
draws =~= past the end and Emacs lets the last line reach the top of the window.
=(set-scroll-past-end nil)= is the way out, and =*mode-settings*= carries it so a
mode can claim either answer.

*The buffer is not touched.* No newline is inserted; the only thing that moved is
the clamp, which is why this is nine lines in core and nothing at all in the
renderer — the draw loop and =offset_at= both stop at =len_lines()= and always
did, so the rows past the end hold no text, the gutter numbers none of them, and
a click in one is =point-max= by the arm that has always answered a click under a
short file. Point cannot follow the view out there either, and that is one call
rather than a guard: the limit is =last_line()= and not =len_lines() - 1=, so the
cursor =scroll_lines= drags along lands on a line =G= would visit, never on the
empty string a trailing newline leaves behind.

Generated buffers — dired, magit, a terminal, the dashboard — keep the old clamp
whatever the setting says. Their text is a rendering of state rather than a
document, so there is no past the end of one; the same instinct takes the gutter
off them.

** Inline images

=crates/render/src/lib.rs=. An image substitutes =ceil(width / cell_w)= blank cells
and is blitted over them; nothing to its right moves. So a wide inline image
overhangs by at most a rounding cell, and a =display= string longer than what it
replaced pushes nothing — it paints over it.

*Height* is no longer in that list. A line's row count is
=max(rows its text wraps into, rows the image on it needs)= — the only thing in the
renderer with an opinion about how tall a row is — and =image_rows= places every
bitmap by one rule: its baseline lands on the baseline of the last row it was
given. An inline =$x_1$= is shorter than the ascent, gets one row and hangs its
depth below the text baseline; a display equation claims whole rows *upward*, into
rows the line grew to hold rather than over the text above. A fragment spanning
several source lines already owns a blank row per line — the substitution blanked
them — and is charged only the shortfall, which is why =\begin{equation}= is
unchanged.

Wide characters used to be filed here as wanting the same thing. They turned out
to want less: a character occupying several *cells* is what a tab already was, so
=char_cells= and one extra blank cell in =expand_line= was the whole fix.

*Rows* used to be filed here too, and this is the entry that says why they are
not, because the answer was that **the boundary did not have to move at all.**

The bug read like a boundary problem: a click below a display equation landed a
row or two high, and scrolling clamped against a pane taller than what was drawn.
The tempting reading — the one this file used to carry, and =TODO.org= with it —
was that core had to be handed the overlay list, or a cell width, or a per-line
row count, so it could lay a line out the way the renderer does. None of that
was true. Every one of the four functions that spends a row lives in
=crates/render=: =Renderer::draw_document= grew a line to hold its bitmap, and
=line_rows=, =visible_lines= and =offset_at= charged it the rows its *text*
needed. The renderer disagreed with itself. Core was never told a wrong number
by the wrong channel; it was told a wrong number by the right one, because
=viewport_lines= is computed *by* =visible_lines= and parked on the =Window=
exactly as =wrap_cols= is.

So the fix is one function — =image_tall= — asked by all four loops, and the
channel to core is unchanged. What it cost: an =Editor::has_images= (one
=is_empty=) so a session that has never rasterised anything does not pay for a
second scan of a line's overlays, and =image= joining =reshapes_lines=, without
which a *truncating* pane took the fast path and reported its full height
regardless. Measured against the running editor, a 68-line file with one
=$$…$$= in a 37-row pane: =(window-height)= answered 36 with the fragment as
source and 36 with it typeset — while drawing 34 — and now answers 34, which is
the number the gutter's last line agrees with.

What is left is that *core* does not see the *pixels*, and it is now only the
horizontal half. Sharing the overlay list closed the text half — a =display=
substitution is counted by both sides, see "Visual lines reach core through one
integer" — and =Editor::line_cells= still counts an image's *source* text rather
than the cells its bitmap reserves, because a cell's width in pixels is the
renderer's alone. Ceiling: =j= onto a line carrying an inline =$x_1$= lands off
by the difference between the fragment's source and its bitmap's width. Upgrade
path is the one this entry always named and it is now for columns only: park a
cell width on the =Editor= the way the renderer already parks =wrap_cols=.

Two neighbours were considered and deliberately left alone. =j= over an equation
is still *one* buffer line, which is right rather than pending: the rows a bitmap
claims hold no characters, so there is nothing in them to land on, and Emacs'
=next-line= over an image moves one line too. And =Window::scroll= is still a
buffer line — see the folding entry above, which is the same ceiling and the same
upgrade, a scroll position of (line, row).

Uploaded textures are never evicted, and neither are the bitmaps in
=Editor::images= that outlive... nothing: core drops a bitmap when the last
overlay naming it goes, and the renderer's texture for it then sits there until
exit. Bounded by the distinct fragments a session previews, which is small.

** Key sequences

=crates/core/src/lib.rs=, =normalize_keys=. ="gg"= means the sequence =g g=, so an
unseparated mix like ="g<tab>"= is not supported — write ="g <tab>"=.

Also =Key=: *fifteen* named keys now carry modifiers — the six that were here
(=C-<ret>=, =C-M-<ret>=, =M-<ret>=, =M-<bs>=, =M-<left>=, =M-<right>=), =<backtab>=,
and the shifted eight org's structure keys are spelled with (=S-<ret>=,
=M-S-<ret>=, the four =S-= arrows, =M-S-<left>=, =M-S-<right>=) — where this note
set the threshold at four. The enum still owes a modifier bitset over a =Named=
enum, and the debt is still a match arm in every crate that reads a =Key=. The
shifted keys were added as more named variants anyway: eight arms in four crates
is a duller change than rewriting ~400 =Key::= sites across fifteen files, and the
bitset does not become worth its blast radius until a spelling arrives that a
variant cannot express at all.

** A type size scales the line, not the run

=crates/render/src/lib.rs=, =line_box=. This is what closed "emphasis is
colour-only": an overlay carries =weight=, =slant= and =scale=, the renderer opens a
face per size and style, and =org-modern= sets all three. Weight and slant are per
*cell*; the size is not.

A scaled cell is wider as well as taller, and where a line wraps, which column
the cursor is in and which character a click lands on are all counted in whole
cells of one width. So the widest scale claimed by any overlay touching a line
sets that whole line's type. =*this* word bigger= is not expressible; a heading is,
which is the case that asked. The upgrade path is the per-line table of cell
advances =draw_image= already names for its own horizontal reflow — one table,
both problems.

The size is also *snapped* to one of four steps. A face plus a texture per
character it draws is what a size costs, so the ladder is the glyph cache's bound
made visible in the vocabulary instead of hidden in an eviction policy.

A themed *span* — what the highlighter produces — is still colour-only, and that
part is not a ceiling but a boundary: a span is recomputed from scratch on every
keystroke, and weight is something a mode *puts* rather than something a parser
derives.

** Two render colours are not settable

=crates/render/src/lib.rs=: the modeline highlight and shadow shades, and the
window divider seam, are hardcoded. A theme that wants a coloured seam has no
reader or writer for it.

** A terminal consults only the =terminal= keymap — *closed*

Was: =terminal_key= looked in the ="terminal"= map, then — for the keys
=Key::is_editor_key= reserves — in ="normal"=, and never at the buffer's own
modes at all, so =(define-key "ai-mode" "C-M-r" ...)= was *silently inert*
inside a session. The upgrade written here was "the same major/minor lookup
=normal_key= already does, moved into =terminal_key=".

That is what landed. =crates/core/src/evil.rs=, =terminal_key= asks
=mode_binding= before =keymap_lookup=, so the buffer's minor modes and then its
major mode win over the ="terminal"= state — the narrower map first, which is
the precedence =normal_key= already gives them.

What did *not* move is the prefix half. =normal_key= lets a mode-local prefix
outrank a global exact binding and waits for the rest of the sequence; a
terminal takes exact bindings only. Waiting is free in a file buffer and costs
the keystroke here — the first key of a =C-c C-e= would be held back from a
program running right now — so a session binding is one chord, and the
multi-key ones stay in the Normal buffer you step out to.

** One terminal grid reaches the renderer — *closed*

Was: =Term::screen= answered one grid and =crates/render/src/lib.rs= took a
single =Option<&Screen>= for the whole frame, so a *split showing two terminal
buffers at once* painted the live session's grid in both panes. The upgrade
written here was "the renderer taking a grid per =BufferId=".

That is what landed. =Term::screens= answers =Vec<(BufferId, Screen)>= and
=Renderer::render= takes =terminals: &[(BufferId, Screen)]=, so a pane finds its
own session's grid or draws none.

** A parked buffer is reverted but not re-highlighted — *closed*

Was: =crates/core/src/lib.rs=, =revert_buffer= *cleared* a parked buffer's
highlight spans rather than getting them recomputed, because the app only ever
asked the syntax thread about the live buffer — so a file an agent rewrote was
correct and colourless until you looked at it. The upgrade written here was "a
parse queue keyed by buffer rather than one slot keyed by revision".

That is what landed, in all four places the one slot showed up. =revert_buffer=
pushes the buffer onto =Editor::pending_highlight=, the same "core records, the
app performs" channel =pending_hooks= uses. =request_pending_parses= in
=crates/app/src/main.rs= drains it and asks for a full parse of each, skipping
the live buffer because the revision path already asks with the change log in
hand. The worker keeps one pending =Request= *per buffer* and parses the newest
first, so a directory reverting at once cannot get in front of the character you
just typed. =Session= keeps up to four trees keyed by =BufferId= rather than
one, so a parked file's parse no longer evicts the tree of the buffer being
typed into — which also closes the "switching between two large files reparses
each time" ceiling that sat in that crate.

The staleness guard the revision compare gave is kept and made per-buffer, which
is what it should always have been: spans are adopted only if the buffer's own
=change_count= *and* its language still match what the text was snapshotted
under. A global revision could not answer that question — a keystroke in the
live buffer moved it and threw away a parked buffer's perfectly good parse.

** M-x offers the readers too

=runtime/library.lisp=, =refresh-commands=. It publishes every zero-argument function
in the package, and the readers are zero-argument functions — so =M-x point=,
=M-x buffer-info= and =M-x font-size= are all in the list, and all of them work
(the value is echoed into the status line). If that is noise rather than
introspection, =*hidden-commands*= in =library.lisp= is the lever.

** A =/ssh:= buffer is four features thinner than a local one

=crates/tramp= is wired into =find-file=, =save-file= and dired: =(find-file
"/ssh:user@host#2222:/etc/nginx.conf")= opens a buffer, =(save-file)= writes it
back atomically, =(dired "/ssh:host:/etc")= lists the directory, and =RET= on a
line in that listing comes back round through =find-file=. Everything reaches the
worker thread in =app/main.rs= (=Remote=) and lands on a later frame, exactly as
[[file:threading.org][threading.org]] says the file commands do — several frames later rather than one,
which is the only difference a config can observe.

Four things a local buffer gets and a remote one does not. Each is a decision
rather than an oversight, and each has a different reason:

- *auto-revert is off.* The sweep =stat=s every open file four times a second.
  Over ssh that is a network round trip per buffer per 250 ms. A remote file
  that moves underneath you is noticed when you next open it. The upgrade is a
  second, much slower timer going through the worker.
- *numbered backups are not taken.* =~/.zemacs.d/backup/= holds copies made with
  =fs::copy=, and the remote equivalent is a whole file transfer per save. The
  *tearing* half of the promise is not lost — the remote write is
  temp-then-=mv=, the same shape =write_file= uses here — only the "give me back
  the version before last" half. The upgrade is one line in =tramp='s
  =write_script=, which already copies the target aside and then throws the copy
  away.
- *"changed on disk — save anyway?" never fires*, because =Buffer.visited= is
  compared against a local =stat=. Asking properly is a round trip per save.
- *auto-save is on, and local.* =~/.zemacs.d/auto-save/#!ssh:host:!etc!nginx.conf#=
  — the crash copy belongs on the machine that crashes, and it is offered back
  on the next open because the =stat= that opening already does carries the
  host's mtime. This is the one that could not be skipped: it is the difference
  between a shortcut and data loss.

One smaller one. The file prompt does not complete remote paths — a listing per
keystroke over ssh — so what you type is what is opened, and dired's =R= and =C=
prompts go bare over ssh for the same reason: their candidates would be *this*
machine's files, and =Prompt::value= prefers the highlighted candidate to the
text, so a remote rename would submit a local path.

A remote dired listing used to be read-only, and is not any more. =rename=,
=copy=, =delete=, =x=, =+= and =C-c n= run on the host the listing came from,
through the same =zemacs-tramp= operations =find-file= and =save-file= use, and
— the part that mattered — through the same confirmation funnel: =D= and =x=
arrive as one =EditorCommand::Dired=, are asked about *by name* before anything
is sent, and both land in =remove_all=, which is still the one place in the
editor that destroys a file. =tramp= grew the two primitives it was missing:
=copy= (=cp -R -P=, refusing an existing destination and a directory copied into
itself) and =create_file= (=set -C=, so an existing name fails in the kernel
rather than being quietly truncated).

They go through the *same worker* the listing does, so a wedged host is a
message and not a frozen editor: dired pushes the [[file:../crates/tramp/src/lib.rs][=tramp::Op=]] onto =want_op=,
=App::housekeep= drains it once a frame, and the answer lands several frames
later — the promise [[file:threading.org][threading.org]] already makes for =find-file=. Draining once
a *frame* rather than under =EditorCommand::Dired= is the whole of why it works:
every one of these verbs arrives as =EditorCommand::Confirmed= or out of the
file prompt, so a per-arm drain reached none of them, and the next verb added
through a fourth door would have been unsent again. The count survived the move
— =remove_all= used to write "deleted 3, failed 1" out of one =Result=, and now
starts a =Deleting= tally that =Dired::did= closes one answer at a time, so it
is still one sentence naming which file stayed.

Two things are still not what a local verb is. Marked files are one round trip
each — a =tramp::Op= names one path, so =x= over four of them is four =rm=s,
queued together rather than run one after another — and the listing on screen is
the pre-verb one until the re-read queued behind them comes back, a few frames
of a stale row. And a remote file whose name contains a newline remains
invisible to all of them, because it never reaches a listing at all (=entry= in
=crates/tramp/src/lib.rs=, whose records are newline-separated): deleting the
directory above such a file works, deleting the file does not, since there is no
line to put the cursor on.

* Where to add things

| You want to add            | Touch                                                        |
|----------------------------+--------------------------------------------------------------|
| A convenience function      | =LIBRARY_FORM= in =crates/lisp/src/shim.c=, or your own config.  |
| A reader                    | =crates/core/src/query.rs= (one =match= arm) + =QUERIES_FORM=.    |
| A reader whose answer needs a crate *downstream* of core | =ask_here= in =crates/lisp/src/lib.rs= + =QUERIES_FORM=. =latex-fragments= and =fold-ranges= are both there: =zemacs-syntax= depends on core, so =query.rs= can never call it. |
| A command verb              | =command_for= in =crates/lisp/src/lib.rs= + a =DEFUN= in =shim.c=. |
| A primitive with an odd shape | =shim.c= (=f_*= + =defprim= + =PACKAGE_FORM=) and =lib.rs= (=rs_*=). |
| A built-in verb             | =run_action= and =BUILTIN_COMMANDS= in =crates/core/src/evil.rs=. |
| A new =EditorCommand=         | =crates/core/src/lib.rs= — and then =needs_app= if the app has to carry it out. |
| A question to ask the user  | Nothing. =read-string= / =completing-read= in your config, and the rest of the command inside the callback. |
| *One keystroke*, against the document rather than a prompt | Nothing. =(grab-key 'your-function)=, and the next key arrives as =(your-function "a")= spelled the way =key-bindings= spells one — including the keys that are not yours, which is what makes cancelling total. =runtime/modes/avy.lisp= is the worked example. |
| An overlay property Lisp alone reads | Nothing. =overlay-put= already stores any object; only the renderer's four cross into Rust. |
| An overlay property the *renderer* draws | A field on =Overlay= and an arm of =OverlayEdit= in =crates/core/src/overlay.rs=, a verb in =command_for=, a =case= arm in =OVERLAY_FORM=, and the drawing in =crates/render=. =fold= is the worked example, and the only one that also had to reach the *motion* code. |
| A mode that can fold        | Two entries in =*fold-subtree-functions*= / =*fold-all-functions*= and one Lisp function. Nothing in Rust. |
| A language server           | One =(lsp-register-server 'mode "program")= in your config. Nothing in Rust. |
| Another JSON-RPC child      | =rpc-start= in Lisp. Nothing in Rust.                        |

Every new primitive, reader or helper gets a test in a *new* file under
=crates/lisp/tests/=. ECL boots once per process, so there is exactly one =#[test]=
per test file; a new file is the only way to add one.
