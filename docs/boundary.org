#+TITLE: The boundary
#+SUBTITLE: what belongs in Lisp, what belongs in Rust, and every known ceiling

* The rule

#+begin_quote
You should be able to do anything in Lisp, but also do performance-intensive
stuff in Rust.
#+end_quote

Which means the Lisp API is judged on *reach*, not on size: nothing about the
editor should be unreachable from the image. It is not judged on speed, because
the heavy lifting stays behind primitives.

Concretely:

| In Rust                                     | In Lisp                                    |
|---------------------------------------------+--------------------------------------------|
| The rope, and every edit to it               | Which edit to make, and when               |
| tree-sitter parsing and highlight spans      | What colour each highlight class is        |
| Glyph rasterisation and the frame            | Font size, theme, modeline geometry        |
| The vim grammar: counts, operators, motions  | Every key binding on top of it             |
| Window layout arithmetic and hit-testing     | When to split, close, focus                |
| Characters to cells, and where a line wraps  | Nothing — there is no reader in cells      |
| Reading and writing files, git, ripgrep, PTYs | Which file, which verb, and what to do next |
| Mode *storage*: one name plus a list         | The whole mode *system*                     |
| A child process, JSON framing, JSON decoding | Every protocol spoken down it, LSP included |

The subprocess row is the newest and the same argument. =crates/rpc= spawns the
child, frames =Content-Length= messages, hands each decoded message to the image
as a *Lisp form*, and knows nothing about =initialize=, capabilities or
diagnostics — all of which live in =runtime/lsp.lisp=, where adding a third
language server is one line and no rebuild.

The mode row is the clearest case. Rust knows a buffer has a =major_mode= string
and a =minor_modes= list, and that entering a mode means "call =X-hook=". It knows
nothing about inheritance, exit hooks, mode-local settings, or picking a mode
from a filename — all of which are Lisp, in =runtime/modes/modes.lisp=, for
exactly the reason Emacs builds them in elisp rather than in C: *that is the part
every config wants to bend, and the image is where bending costs nothing.*

* How to decide where a new thing goes

In order. Stop at the first one that works.

1. *Can it be written as a Lisp function over what already exists?* Write it
   there. =switch-to-buffer=, =save-excursion=, =replace-all=, =where-is= and
   =buffer-lines= are all in this category, and none of them is a primitive.
2. *Is it a new question about editor state?* Add a reader: one arm of the
   =match= in =crates/core/src/query.rs= and one name in the list in =QUERIES_FORM=.
   Nothing in C.
3. *Is it a new command whose arguments fit "a verb, maybe a string, up to two
   integers"?* Add a verb: one arm of =command_for= in =crates/lisp/src/lib.rs= and
   a one-line =DEFUN= in =shim.c=. Nothing in C.
4. *Does it need a shape those two envelopes cannot carry* — floats going out, a
   handle coming back? Then it earns a C primitive. =set-background= (three
   floats) and =%make-marker= (a handle) are the two kinds.
5. *Is it hot enough that Lisp doing it per keystroke would be felt?* Then it is
   Rust, and Lisp gets a knob rather than a hook. Highlighting and layout are
   here.

The asymmetry is deliberate. Adding to Lisp costs a line. Adding a C primitive
costs a Rust function, an =extern=, a C wrapper, a =defprim= and an export — five
places that can drift out of step. A helper beats a primitive; composition beats
a new entry point.

* What is genuinely unreachable from Lisp

These are not oversights and not shortcuts: each needs a new =EditorCommand=
variant or a new accessor in =crates/core/src/lib.rs=, which is the one file the
Lisp side cannot work around.

| Missing                              | What is in the way                                                      |
|--------------------------------------+-------------------------------------------------------------------------|
| Interrupt a runaway form             | The Lisp thread evaluates one queued form at a time and nothing can preempt it. |

That table used to have seven rows. Six of them were closed by *six =%do= verbs
and two accessors* — no new C primitive, no new =defprim=, nothing in =shim.c=
except Lisp — which is the ladder above working exactly as intended: what looked
like "the Lisp API needs a way in" was, every time, one arm of =command_for= and
one arm of =Editor::apply=.

| Was missing                          | What closed it                                                          |
|--------------------------------------+-------------------------------------------------------------------------|
| Create a buffer with no file behind it | =(create-buffer name &optional language)=, verb ="create-buffer"=. Idempotent by name, applied on the spot, an *ordinary* buffer rather than a generated one. |
| Kill a buffer                        | =(kill-buffer &optional name)=, verb ="kill-buffer"=. The last one is refused; windows showing it follow the live buffer. |
| Get an answer back from the user     | =(read-string label callback)= and =(completing-read label candidates callback)=, verbs ="read-from-minibuffer"= and ="prompt-item"=. See below — it is a continuation, not a blocking read. |
| Send a keystroke to the shell        | =(term-send-key key)=, verb ="term-key"=, over =Key::from_token= — the inverse of the =Key::token= that =key-bindings= already reports. One vocabulary, both directions. |
| Run a built-in verb by name          | =(call-command name)=, verb ="call"=. =Editor::run_action= is public and answers a *batch*, so the verb is resolved in =rs_do= beside =paste= rather than in =command_for=. |
| Group several edits into one undo step | *Nothing, deliberately.* See below. |

** The prompt continuation, and why it is not a blocking read

The valuable one, and the only one whose shape needed thinking about. Every
other =PromptKind= has its destination fixed in core — a file is opened, a
command is run — and this one hands the reply to a Lisp closure.

It could not be =(setf answer (read-string "Name: "))=. The Lisp thread evaluates
one queued form at a time, so a primitive that waited on a keystroke would stop
*the image* — every mode hook, every key bound to a Lisp command, every =M-x= —
until the question was answered. That is precisely the elisp behaviour
[[file:threading.org][threading.org]] exists to avoid, and paying it back here for one convenience would
undo the whole design.

So the answer arrives the way a JSON-RPC reply already does, on purpose rather
than as a second mechanism: the closure is parked in =*prompt-continuations*=
under an id, the id rides into core inside the command, and accepting *or
cancelling* the prompt makes core emit =CallLisp= of =(%prompt-reply ID ANSWER)= —
the one route core has to reach the image, and the same one a mode hook takes.
Cancelling replies =NIL= rather than staying silent, so a callback is always
called exactly once and a command can clean up in it.

The id exists for the same reason =rpc-request='s does: a stale reply is dropped
rather than delivered to whoever asked most recently.

** Grouping N edits into one undo step: closed by argument, not by a feature

This row is gone because the mechanism should not exist, not because it was
built.

Every mutating primitive checkpoints *inside itself*, so "begin an undo group"
means one of two things, and both are worse than the alternative:

- a flag that makes the mutators skip checkpointing until it is cleared — which
  is left set forever the first time a Lisp error escapes between =begin= and
  =end=, and an editor that has quietly stopped recording undo is a far worse
  failure than N undo steps;
- a nesting counter with the same failure mode plus =unwind-protect= discipline
  at every call site.

And it would not even buy what it looks like it buys. Grouping makes N edits
*undo* together; it does nothing about the gap between them, so a keystroke can
still land in the middle and be typed into a half-finished edit. The thing that
fixes both is already there: build the whole text in Lisp and apply it with one
=replace-region=, which is one lock, one undo step and no gap. =replace-all= in
the standard library is exactly this, and it is why =replace-region= exists next
to =delete-region= and =insert=.

The table in [[file:threading.org][threading.org]] is the documentation this row wanted.

* Known ceilings that a config will actually feel

These are deliberate shortcuts, marked =ponytail:= in the source. Each names its
ceiling and its upgrade path where the source does.

** The shim returns bytes, not characters

=crates/lisp/src/shim.c=, =f_query=. Query answers arrive as an ECL *base* string,
so buffer text is its UTF-8 bytes rather than its characters.

- Round-trips are byte-exact, including emoji.
- =(length (buffer-string))= counts bytes. Use =(point-max)= for characters.
- =search-forward= and =search-backward= convert, so their answers are character
  offsets — but a non-ASCII *literal in a =load=ed file* is an extended string and
  will not match non-ASCII buffer text at all.

Upgrade path: decode into an extended string in =f_query=. Worth doing when a
config genuinely does arithmetic on non-ASCII text.

** Visual lines reach core through one integer

=crates/render/src/lib.rs=, =Renderer::render=. Where a line wraps depends on the
font, the pane and the gutter, none of which core can see — so the renderer parks
=wrap_cols= on each =Window= and on the =Editor= every frame, exactly as it does
=viewport_lines=, and core does the row arithmetic itself over
=crates/core/src/display.rs=. That is the whole channel; there is no second one.

Two consequences a config will feel:

- =0= means "nothing has drawn this window yet", which every reader takes as *no
  wrapping*. A Lisp-only or headless =Editor= moves by buffer line.
- Core lays a line out *without* overlays, so a =display= substitution — an
  org-modern bullet, ghost text — shifts the renderer's columns and not core's,
  and =j= down such a line can land a character off. Upgrade path: =substitute=
  moves into =display= too and =Editor::line_cells= takes the buffer's overlays,
  which is the list the renderer already walks.

With an operator pending, =j= and =k= are still *buffer* lines: =dj= deletes two
whole lines, as in vim. Emacs' =evil-next-visual-line= is an exclusive motion and
would delete to the same column one row down.

** Switching buffers fires no hook

=runtime/modes/modes.lisp=, =%enter-major-mode=. The editor reports a mode being
*entered* and never a buffer being *switched*, so settings claimed by a mode
follow the last mode entered rather than the buffer on screen. Two org buffers
are fine; flipping between an org buffer and a rust one with =C-M-j= is not.

Upgrade path: a hook on the buffer switch — a line in core, not in Lisp.

** The settings baseline starts at the factory default

=runtime/modes/modes.lisp=, =%wrap-setting-primitives=. The mode system wraps each
setting primitive to record what a config asked for. A setting changed *before*
=modes.lisp= is loaded is not seen, so load it above your appearance settings.

This one is now half-closed: every setting has a reader (=(font-size)=,
=(tab-width)=, =(line-overflow)= …), so the baseline could be read rather than
assumed. That change belongs in =modes.lisp=.

** A change notification carries no delta

=crates/app/src/main.rs=. The editor now reports =after-change-hook= when the
document's revision moves, but it reports only *that* it moved — core keeps no
edit log a reader could walk, so Lisp has to read the buffer back to find out
what happened.

The visible cost is in =runtime/lsp.lisp=: =textDocument/didChange= sends the
**whole buffer** on every keystroke rather than a range. That is one buffer copy
per revision, which is what Emacs paid for years and is not felt below a few
hundred KB.

Upgrade path: core recording =(start, old-end, new-end)= per edit and handing it
to the hook. It is the same record overlays want, so it should be built once for
both rather than approximated by diffing two copies of a buffer here.

** LSP columns are characters, not UTF-16 code units

=runtime/lsp.lisp=. LSP counts a column in UTF-16 code units and this editor
counts characters, so the two agree exactly on ASCII and disagree on a line with
an accent before the cursor — a jump lands a column or two off.

Upgrade path: a reader that answers a line's UTF-16 prefix length, which is an
arm of the =match= in =query.rs=. Negotiating =utf-8= with the server would only
trade one mismatch for another, since that spelling means *bytes*.

** Buffers are matched by name

=crates/lisp/src/shim.c=, =with-current-buffer=. Two files with the same base name
are indistinguishable and the first wins. Upgrade path: a reader keyed by buffer
id, which needs the ids exposed first.

=create-buffer= and =kill-buffer= are matched the same way and inherit the same
ceiling — which is also what makes =(create-buffer "*Messages*")= idempotent, so
here it is the feature rather than the shortcut.

** A Lisp prompt left open by another prompt

=crates/lisp/src/shim.c=, =PROMPT_FORM=. A =read-string= is answered on accept
*and* on cancel, so its continuation is always called — unless Lisp opens a
second prompt over the top of the first, which replaces the =Prompt= core is
holding and strands the closure in =*prompt-continuations*=.

A few conses, and only reachable from a config that puts a picker up from inside
a =read-string= rather than from its callback. =(clrhash *prompt-continuations*)=
is the sweep; the upgrade path is core replying =NIL= to the prompt it is about
to discard, which is three lines in =open_prompt=.

** A buffer Lisp made is not read-only

=crates/core/src/lib.rs=, =Editor::create_buffer=. =BufferKind::is_generated= is
what makes =*magit*= and =*dired*= refuse an edit, and a created buffer is
deliberately not one of those — Lisp owns it, so it has to be writable. The cost
is that =*Messages*= can be typed into, and the typing is thrown away the next
time the command regenerates it.

Upgrade path: a per-buffer read-only flag rather than a kind, which is what
Emacs has and what a =*xref*= listing will want too.

** Markers

- =crates/core/src/lib.rs=, =step_history=: undo restores a whole snapshot rather
  than replaying edits, so a marker beyond the restored end is *clamped* onto it
  rather than restored exactly. Never outside the document, which is the
  invariant a marker owes its holder.
- =crates/lisp/src/shim.c=: =(make-marker)= puts one *at point* rather than
  nowhere, and the insertion type is fixed at creation — there is no
  =set-marker-insertion-type=.
- =crates/core/src/marker.rs=: markers are a =Vec= scanned linearly, which is right
  for a few per buffer and wrong for one per hit of a search.

** Overlays

- =crates/core/src/overlay.rs=: an overlay's colours are *face names* from
  =face-list=, never an =(R G B)=. That is what keeps every overlay writer inside
  the =%do= envelope and out of C, and what makes an overlay follow =load-theme= for
  free. An overlay wanting a colour no face has must =set-syntax-color= a spare
  face first; the upgrade path is a primitive taking three floats, the shape
  =set-background= already has.
- The insertion types are fixed at Emacs' defaults — text typed at the front
  lands inside, text typed at the back lands outside — so there is no
  =front-advance= / =rear-advance=.
- An overlay whose text is entirely deleted is deleted with it, where Emacs would
  keep a zero-width one. Every payload here is *about* the text underneath, and a
  =display= string over no text is a ghost.
- =crates/lisp/src/shim.c=: the property list lives in the image, keyed by handle.
  =delete-overlay= and =remove-overlays= prune what they remove, but an overlay the
  *editor* deleted — because an edit swallowed its text — leaves a few conses
  behind. The comment above =OVERLAY_FORM= has the one-line sweep.
- =fold= is the one property that is about *lines*: it makes the lines after the
  overlay's first stop occupying rows. Two-state only — a fold is closed or open,
  and opening one opens every fold inside it, which is org's =SUBTREE= and never
  its =CHILDREN=. Folding is per *buffer line*, so half a line cannot be hidden;
  the head line is always drawn, and there is no way to fold from the very top of
  a buffer with nothing above the region.

** Folding does not follow the scroll position exactly

=crates/render/src/lib.rs=, =visible_lines=. A folded line counts as a *line* and
costs no *row*, which is what lets =scroll= step over a fold — but the pane's row
budget is checked before each line is charged, so a run of folds at the very
bottom of the count is not reached. =viewport_lines= then under-reports slightly,
which lets the view scroll one screen further than it strictly needs to. That is
the safe direction; the other one would make the end of the file unreachable.

=Window::scroll= is still a *buffer line*, so scrolling to a line that is folded
lands the pane on the first drawn line after it. Upgrade path is the same one
wrapped lines want: a scroll position of (line, row).

** Inline images

=crates/render/src/lib.rs=. An image substitutes =ceil(width / cell_w)= blank cells
and is blitted over them; nothing to its right moves. So a wide inline image
overhangs by at most a rounding cell, and a =display= string longer than what it
replaced pushes nothing — it paints over it.

*Height* is no longer in that list. A line's row count is
=max(rows its text wraps into, rows the image on it needs)= — the only thing in the
renderer with an opinion about how tall a row is — and =image_rows= places every
bitmap by one rule: its baseline lands on the baseline of the last row it was
given. An inline =$x_1$= is shorter than the ascent, gets one row and hangs its
depth below the text baseline; a display equation claims whole rows *upward*, into
rows the line grew to hold rather than over the text above. A fragment spanning
several source lines already owns a blank row per line — the substitution blanked
them — and is charged only the shortfall, which is why =\begin{equation}= is
unchanged.

Wide characters used to be filed here as wanting the same thing. They turned out
to want less: a character occupying several *cells* is what a tab already was, so
=char_cells= and one extra blank cell in =expand_line= was the whole fix.

What is left is that *core* does not see any of it. =visible_lines= and
=cursor_pane_row= count a line's text rows only, so a pane showing a display
equation reports a line or two more than it draws (=viewport_lines=, which core
clamps scrolling against) and a relative gutter number below one is short by the
rows the image took. That is the same ceiling as "core lays a line out without
overlays" above, and the upgrade is the same: hand both of them the overlay list
=draw_document= is already walking.

Uploaded textures are never evicted, and neither are the bitmaps in
=Editor::images= that outlive... nothing: core drops a bitmap when the last
overlay naming it goes, and the renderer's texture for it then sits there until
exit. Bounded by the distinct fragments a session previews, which is small.

** Key sequences

=crates/core/src/lib.rs=, =normalize_keys=. ="gg"= means the sequence =g g=, so an
unseparated mix like ="g<tab>"= is not supported — write ="g <tab>"=.

Also =Key=: three named keys carry modifiers (=C-<ret>=, =C-M-<ret>=, =M-<bs>=) and
the enum will become a modifier bitset at four.

** Emphasis is colour-only

=crates/core/src/lib.rs=, =HlKind=. The renderer opens exactly one font face, so
=bold= and =italic= are carried by colour rather than by weight or slant. Themes can
choose the colour; they cannot ask for real bold.

** Two render colours are not settable

=crates/render/src/lib.rs=: the modeline highlight and shadow shades, and the
window divider seam, are hardcoded. A theme that wants a coloured seam has no
reader or writer for it.

** A terminal consults only the =terminal= keymap

=crates/core/src/evil.rs=, =terminal_key=. =normal_key= layers the buffer's minor
modes, then its major mode, then the modal state, then the grammar. A terminal
does none of that: it looks in the ="terminal"= map, then — for the keys
=Key::is_editor_key= reserves — in ="normal"=, and everything else goes to the
child. So =(define-key "ai-mode" "C-M-r" ...)= is *silently inert* inside a
session, and the session verbs in =runtime/modes/ai.lisp= are bound in the
="terminal"= state instead. That is fine while every verb means something in a
shell too; the fix, when one does not, is the same major/minor lookup
=normal_key= already does, moved into =terminal_key=.

** One terminal grid reaches the renderer

=crates/app/src/term.rs=, =Term::screen=, and =crates/render/src/lib.rs=, which
takes a single =Option<&Screen>= for the whole frame and draws it in every pane
whose buffer is a terminal. Sessions are plural and grids are not, so a *split
showing two terminal buffers at once* paints the live session's grid in both.
Everything else about a background session is correct — its buffer text, its
name, its size, and its own pane the moment you focus it. The upgrade is the
renderer taking a grid per =BufferId=.

** A parked buffer is reverted but not re-highlighted

=crates/core/src/lib.rs=, =revert_buffer=. Auto-revert now follows every open
buffer, and a buffer whose text was replaced while parked has its highlight
spans *cleared* rather than recomputed — the app only asks the syntax thread
about the live buffer. So a file an agent rewrote is correct and colourless
until you look at it, at which point the revision bump gets it parsed. The
upgrade is a parse queue keyed by buffer rather than one slot keyed by revision.

** M-x offers the readers too

=runtime/init.lisp=, =refresh-commands=. It publishes every zero-argument function
in the package, and the readers are zero-argument functions — so =M-x point=,
=M-x buffer-info= and =M-x font-size= are all in the list, and all of them work
(the value is echoed into the status line). If that is noise rather than
introspection, =*hidden-commands*= in =init.lisp= is the lever.

* Where to add things

| You want to add            | Touch                                                        |
|----------------------------+--------------------------------------------------------------|
| A convenience function      | =LIBRARY_FORM= in =crates/lisp/src/shim.c=, or your own config.  |
| A reader                    | =crates/core/src/query.rs= (one =match= arm) + =QUERIES_FORM=.    |
| A command verb              | =command_for= in =crates/lisp/src/lib.rs= + a =DEFUN= in =shim.c=. |
| A primitive with an odd shape | =shim.c= (=f_*= + =defprim= + =PACKAGE_FORM=) and =lib.rs= (=rs_*=). |
| A built-in verb             | =run_action= and =BUILTIN_COMMANDS= in =crates/core/src/evil.rs=. |
| A new =EditorCommand=         | =crates/core/src/lib.rs= — and then =needs_app= if the app has to carry it out. |
| A question to ask the user  | Nothing. =read-string= / =completing-read= in your config, and the rest of the command inside the callback. |
| An overlay property Lisp alone reads | Nothing. =overlay-put= already stores any object; only the renderer's four cross into Rust. |
| An overlay property the *renderer* draws | A field on =Overlay= and an arm of =OverlayEdit= in =crates/core/src/overlay.rs=, a verb in =command_for=, a =case= arm in =OVERLAY_FORM=, and the drawing in =crates/render=. =fold= is the worked example, and the only one that also had to reach the *motion* code. |
| A mode that can fold        | Two entries in =*fold-subtree-functions*= / =*fold-all-functions*= and one Lisp function. Nothing in Rust. |
| A language server           | One =(lsp-register-server 'mode "program")= in your config. Nothing in Rust. |
| Another JSON-RPC child      | =rpc-start= in Lisp. Nothing in Rust.                        |

Every new primitive, reader or helper gets a test in a *new* file under
=crates/lisp/tests/=. ECL boots once per process, so there is exactly one =#[test]=
per test file; a new file is the only way to add one.
