#+TITLE: zemacs — what is left
#+STARTUP: overview

Tracked against the real =~/.emacs.d=, so "missing" means missing *relative to
what is actually used every day*, not relative to Emacs in the abstract.
Ordered by what unblocks the most, not by what is easiest.

* BLOCKING — one hole, many features

** DONE Overlays
=crates/core/src/overlay.rs=: a range that moves with the text, built out of
the marker machinery (one =adjust_pos=, two callers), carrying a face, a
background, a =display= substitution, an image — and, in the image rather than
in Rust, any Lisp object at all.

*No text properties, and there will not be any.* Emacs has both because
properties live in the buffer's string data; a rope of characters is what makes
every offset here a character index, and threading a plist through it would buy
an inheritance rule most configs turn off. One mechanism.

The Lisp API is =make-overlay=, =overlay-put=, =overlay-get=, =overlay-position=,
=overlays-in=, =overlays-at=, =delete-overlay=, =remove-overlays= — one C primitive
(the handle has to come back), everything else =%do= and =%query=.

org-modern bullets and org-appear are *written*, both in Lisp and both on
=display=, in =runtime/modes/org-modern.lisp=. Still to write on the same
mechanism: avy hint labels, copilot ghost text, flymake in the gutter, LSP
inlay hints. Code folding needed a Rust hole of its own — an overlay hid
*cells*, not *lines* — and got one: a fifth property, =fold=, below.

** DONE Inline images in a buffer
Overlay property =image=, whose value is a handle from =(latex-preview source)=.
Pixels live in =Editor::images= keyed by a hash of the job, so the renderer's
texture survives a re-preview; placement uses the baseline depth =crates/latex=
reports, so =$x_1$= hangs below the line.

=org-latex-preview= is *written in Lisp*, in =runtime/init.lisp=, over two
primitives: =(latex-fragments)= to find them and =(latex-preview src)= to
rasterise one.

Bound to =C-c r= — as asked — and also to =SPC m l=. This needed the precedence
change =lisp-mode= made for its own =C-c C-e= family: a mode-local *prefix* now
outranks a global exact binding, so =C-c= waits for the next key in an org
buffer and still evaluates on its own everywhere else. Nothing was given up.

*** DONE Rows of variable height
One integer, in the end. A line's height is
=max(rows its text wraps into, rows the image on it needs)= — the only thing in
=crates/render= that has an opinion about how tall a row is — and =image_rows=
places every bitmap by a single rule instead of the two the old code
special-cased: *its baseline lands on the baseline of the last row it was
given*. An inline =$x_1$= is shorter than the ascent, gets one row, and hangs its
depth below the text baseline the way a descender does; a display equation claims
whole rows *upward*, which is now safe because the line grew to hold them.

A fragment spanning several source lines already owns a blank row per line — the
substitution blanked them — so only the shortfall is charged, and
=\begin{equation}= draws exactly as it did while a =$$…$$= written on one line
stops painting over its neighbour.

Wide characters were the other half of the old justification and turned out not
to need this at all: several *cells* is what a tab already was.

The =viewport_lines= half of this is closed, and the interesting part is that it
needed nothing from core. =image_tall= is now the one answer =draw_document=,
=line_rows=, =visible_lines= and =offset_at= all ask, so a pane holding an
equation reports what it draws and a click below one lands on the line under the
pointer. See the entry in "Open" below, and =docs/boundary.org=.

=j= over an equation is still one buffer line, and that is the answer rather than
the debt: the rows a bitmap claims hold no characters, so there is nothing in
them to land on — Emacs' =next-line= over an image moves one line too. What is
genuinely still open is sideways: the *cells* a bitmap reserves are pixels over a
cell width core has not got.

** DONE A JSON-RPC subprocess layer
=crates/rpc=: spawn a long-lived child, =Content-Length=-framed JSON on its
stdin and stdout, requests / responses / notifications in both directions,
stderr drained, the child dying reported. Three threads per child (reader,
writer, stderr) so nothing can block the editor, and a reply reaches Lisp the
way a mode hook does — the main loop turns each message into a form and queues
it for the Lisp thread. The Lisp side is =runtime/rpc.lisp=, and a config can
drive an arbitrary JSON-RPC child without touching Rust.
*** DONE LSP (eglot equivalent) — pylsp and clangd
All of it in Lisp, in =runtime/lsp.lisp=: handshake, didOpen/didChange/
didSave/didClose, definition, diagnostics. A third server is one
=(lsp-register-server 'rust-mode "rust-analyzer")= in your config — untested
here only because the two shipped are the two it was proved against.
Sync is full-text; see the ceiling in =docs/boundary.org=.
*** DONE xref — find references, and a *xref* results buffer
This entry predicted a generated buffer kind in Rust with its own keymap and a
line-to-location table — the magit/dired shape. It needed none of that, and the
reason is worth keeping: the rows are =PATH:LINE:TEXT=, which is what ripgrep
prints and what =find-file-at= already parses, so **the text *is* the table**.
The read-only flag and the mode were each one call that already existed, and
=runtime/modes/xref.lisp= is the whole feature.

What that buys is what =crates/lisp/tests/xref.rs= mostly asserts: because the
listing is ordinary text, *deleting a row excludes a hit*. Nothing had to be
taught that — it falls out of the listing not being a special kind of buffer.
*** DONE flymake — diagnostics in the gutter
The data was already there — =(lsp-diagnostics)= answering =((LINE COLUMN
SEVERITY MESSAGE SOURCE) ...)=, and =*lsp-diagnostics-functions*= firing when it
changes — so this was only ever the drawing, and the drawing turned out to be
forty lines of Lisp at the foot of =runtime/lsp.lisp=. Nothing above the seam
changed, which was the claim the seam was written to make.

A *mark in the margin* rather than the =background= overlay this entry
predicted, and the reason is the face list: colours on an overlay are named from
=face-list= so a theme change recolours them for free, there is no =error= face
in it, and Lisp cannot add one. Colouring diagnostics would have meant spending
=keyword= on them with =set-syntax-color=, which changes every keyword in every
buffer. Severity goes in the *shape* of the mark instead — =●= error, =▲=
warning, =›= info, =·= hint — which no theme can take away and which reads the
same light or dark. =line-prefix= is what makes it one overlay per diagnostic:
it pushes the line right and draws in the gap, continuation rows included.

The seam alone would have left a file you came *back* to wearing stale marks, so
the buffer switch is noticed on =after-change-hook= — which fires on a switch,
because the revision moves — at a cost of one string compare per keystroke.

What is still missing is the *message* in the buffer, which wants virtual text:
=display= replaces the cells it covers, so an inline message would eat the code
it is about. That is an =after-string= overlay property — a payload in
=overlay.rs= and a branch in the renderer's line loop. =SPC l e= until then.
*** DONE hover a diagnostic mark and read what is wrong
The entry above predicted =after-string= for this and the prediction was for the
wrong feature. =after-string= is right for an *inline* message — text living
permanently at the end of the offending line — and it is wrong for a hover twice
over: it is pinned to the end of a line and the pointer is wherever your hand
is, and it is on until something takes it off where a hover's whole contract is
that it is gone when you look away. The inline message is still unbuilt and
still wants =after-string=. This wanted something else.

*A fourth surface drawn over the frame*, after =ace=, =which-key= and the
completion popup, and the *second* one measured in pixels — =ContextMenu= was
already the first, and for the identical reason: a box hung off the pointer has
no buffer offset for the renderer to convert. So =Editor::tooltip=, one
=(frame, x, y, text)=, and the two pointer-anchored surfaces now share one rule
about what happens at an edge.

*The message rides on the overlay*, as =help-echo= — Emacs' name, spelled the
same. That is the finding worth keeping: it is the one property here that draws
nothing, and it crosses into Rust anyway, because its reader is the mouse and the
mouse is on that side. The alternative was core asking the image "what is at line
40" on hover, which is a round trip on the one path that fires per pixel *and* a
second derivation of a fact the overlay already carries. Hung on the overlay, the
message slides with the text and dies with it, so it cannot come to describe the
wrong line — which is the same argument the mark itself was made an overlay for.

*Motion is the expensive event.* It fires per pixel, and resolving a pixel to a
buffer line means walking the visible lines through folds, wraps and image rows —
a cell vector per line. So the walk is behind a cheap question:
=Renderer::gutter_row=, a pane lookup, one compare against the gutter's right edge
and one division. A gutter mark is a row tall, so the answer cannot change inside
one, and the expensive half runs *once per row crossed*. The cache remembers what
that answered **and whether a box was up when it did** — without the second half,
a keystroke taking the box down while the pointer sits still leaves it stuck until
you cross into the next row.

*Retiring it is four places and not a predicate*, which is where this differs from
the completion popup. =Editor::completion()= can be a predicate because "is point
still in that word" is a question about the editor. Nothing about the editor can
answer "is the pointer still on the mark" — so: motion sets or clears it, a
keystroke clears it beside the context menu in =handle_key=, a click and the wheel
clear it because both move the text under a pointer that has not moved, and
=WindowEvent::MouseLeave= clears it because walking off the edge of the frame
produces no further motion to notice with.

*Only the gutter.* Hovering the offending *span* is a different hit test and does
not fall out, because the diagnostic overlay deliberately covers the whole line —
so a text hit test would fire on every column of every marked line as the pointer
crossed the buffer. It wants a second overlay on the error's own range, which is
=lsp.lisp='s to make; the Rust side would then be =click_target= plus the same
=help_echo_at=. Where there is no gutter there is nothing to hover, and that
falls out rather than being handled: =gutter_row= asks the same =gutter_w= the
draw loop asks before painting a mark, so "there is a mark here" and "there is
something to hover here" cannot come apart. Worth recording that this is not the
same set as =set-no-gutter-modes= names — an =org-mode= buffer opened out of the
shipped config draws line numbers and a diagnostic mark despite being on that
list, which is a separate thing to chase; the hover follows what is *drawn*, so
it was right in a case the design note would have got wrong.

The hit strip is the gutter's columns plus one =PAD= of air, and not everything
left of the text, which was the first cut and was visibly wrong in org: a buffer
with a =text-width= is centred, so its left margin is a third of the window and
the box appeared for a pointer resting nowhere near a mark. =offset_at= is more
generous — it clamps a click in the margin to column zero — and that generosity
belongs to a gesture you aimed.

The chain is tested in =crates/app/tests/control.rs= rather than in
=crates/lisp/tests/=, and that is forced rather than chosen: half of this chain is
arithmetic between a font and a rectangle, and a headless =Editor= has no
renderer, so a test up there could assert that the message reaches the overlay and
not one thing about hovering it. Which needed a way to move a pointer over the
wire — the =mouse= op, in pixels, through the same =App::hover= the SDL arm calls.
Verified against a real =pylsp= by hand as well: four diagnostics on one line from
=mypy= and =ruff= at once, and the newest wins, exactly as the glyph already did.
*** DONE AI mode with multi-agent support
Not the JSON-RPC route in the end, and that is the finding: Claude Code, Cursor
and opencode are all *terminal* programs, and the editor already runs terminal
programs. So the work turned out to be four things, none of them a protocol.

*Sessions became plural.* =crates/term::Terminal= was always one PTY per struct;
what was singular was =Term= in the app, which held one and drove one
=BufferKind::Terminal= buffer through =show_special=. It now holds a =Session= per
child — its own PTY, its own buffer, its own frozen flag — keyed by =BufferId=,
which is what makes a session act like any other buffer: =(buffer-list)= sees it,
=switch-to-buffer= reaches it, =kill-buffer= hangs up on it, and closing one leaves
the rest running. Core grew =show_named= beside =show_special= for it: the match is
on =(kind, given-name)= rather than on kind alone, so one =*magit*= is still one
=*magit*= and =*claude*=, =*claude*<2>= and =*terminal*= are three.

*Change detection got faster and wider.* Auto-revert was one =stat= on the live
buffer every five seconds, which is the right size for "a formatter ran" and the
wrong size for an agent rewriting six files you are not looking at. It is now
every buffer with a file behind it, four times a second, through a new
=Editor::revert_buffer(id, text)= — the =EditorCommand::Revert(BufferId)= the old
ponytail note asked for, as a method, since it performs no effect the pure core
cannot. Still polled rather than watched, and the argument is in the comment
above it: on macOS =notify= is FSEvents, which reports *directories* and coalesces
on its own latency, so it removes the loop and not the syscall — and the loop is
tens of =stat=s against hot inodes. Both safety properties survive and are tested:
a modified buffer is never clobbered, and the comparison is on content so the
buffer that just saved does not revert itself.

*The menu is data.* =runtime/modes/ai.lisp= holds =*ai-harnesses*= as
=(NAME PROGRAM NEW-ARGS RESUME-ARGS)=; =C-a= is =completing-read= over it, then
=new= / =resume=. A fourth tool is =(ai-add-harness "aider" "aider")= and nothing
else — no Rust, no recompile. The resume flags were read out of each tool's own
=--help= rather than remembered (=claude -r=, =cursor-agent --resume=,
=opencode --continue=), and =crates/lisp/tests/ai.rs= re-reads them from the
installed binaries so a rename cannot rot the config silently. =executable-find=
is nine lines of Lisp over =$PATH=, so the menu can say "not installed" instead of
forking a PTY that dies.

*AI mode* is =(major-mode)= answering ="ai-mode"=, an =ai-mode-hook= fired once per
session, and session verbs on Command chords — =C-M-n=/=C-M-b= to walk,
=C-M-r= restart, =C-M-w= close, =C-M-t= out to the scrollback, =SPC a f= to open the
file the agent just mentioned. Deliberately no bare keys: ="terminal"= is the one
state consulted *instead of* the vim grammar precisely so =d=, =j= and =C-c= reach
the child, and typing English at an agent needs that more than a shell does.

Two ceilings, both named in the code. A split showing two terminal buffers at
once draws the live session's grid in both panes, because the renderer takes one
=Option<&Screen>=; the fix is a grid per buffer id and it is a signature change in
=zemacs-render=. And the session verbs are bound in the ="terminal"= *state* rather
than in =ai-mode=, because =terminal_key= consults only the state's keymap — every
verb is meaningful in a shell too, so layering the major-mode map in there buys
nothing yet.

* CONTRADICTS THE EXISTING CONFIG
Worse than missing: these are *wrong* rather than absent, so muscle memory
fights them.

** DONE =j= / =k= move by visual line
A visual line is a *renderer* fact and =j= is a *core* one, so the channel is the
one =viewport_lines= already established: the renderer parks =wrap_cols= — cells of
text a window has across, gutter taken out — on each =Window= and on the =Editor=
every frame, and core does the row arithmetic itself. =0= means nothing has drawn
yet, which is every headless test, so they all still move by buffer line.

Both sides lay a line out with the *same* function: =crates/core/src/display.rs=
(=expand_line=, =visual_col=, =char_cells=) moved out of the renderer so that a =j=
that computed cells differently could not put the cursor where the block is not
drawn. =desired_col= holds a *cell* column during a visual run — on CJK the two
units differ by a factor of two — and a run down and back up through wrapped and
unwrapped lines returns to the same character.

Relative line numbers count visual rows (=display-line-numbers-type 'visual=): a
number on every row rather than one per buffer line, the cursor's own row keeping
its absolute number. They were declared in =Settings= and never drawn at all
before this.

Left open: with an *operator* pending, =dj= is still two whole buffer lines, which
is what vim does and what the tests assert — Emacs' =evil-next-visual-line= is an
exclusive motion and adopting that changes what =dj= means.

A =display= overlay used to be listed here too — it was not applied when core laid
a line out, so =j= down a heading landed a character off. That is closed:
=display::line_cells= is the one layout both sides ask, bullet and checkbox
included. An overlay carrying only an *image* is the remainder, and only
sideways: its cells are pixels over a cell width core has not got, so =j= onto a
line with an inline =$x_1$= is still off by the fragment's source width.

** DONE Free the Option key for unicode
=mac-option-modifier 'none= is set: Option is deliberately kept for composing
characters. Command is now the *only* Meta, and the whole mechanism that
existed to fight Option went with it — an Alt keydown used to arm
=swallow_text= so that the =TextInput= macOS composed from the combo was
dropped, because =M--= had already been dispatched and – would otherwise have
been inserted on top of it. With Option out of the Meta test that text is
exactly what was being asked for, so it is inserted like any other. ⌥- is –,
⌥= is ≠, ⌥u then u is ü, and in a modal mode — where there is no text input to
compose into — Option is simply ignored and the key is the key.

* EDITOR BASICS STILL MISSING
Roughly in the order they would be hit.

** DONE System clipboard
=select-enable-clipboard t= means the unnamed register *is* the clipboard, so
that is what it is: =yy= here pastes into a browser and =⌘C= there is what =p=
puts back. Core owns the register and cannot reach the window system, so the
mirror lives in the app layer — pushed once a frame off a revision counter (an
integer compare, not a string diff), pulled on SDL's =ClipboardUpdate= event
rather than by polling the window server sixty times a second.
Text arriving from outside is treated as linewise only if it ends in a newline,
which is what =yy= would have produced. Not done: the =+= and =*= registers as
*separate* registers, and the X11 primary selection.
** DONE Named registers (only the unnamed one exists)
=""ayy"=, =""ap"=, =""aP"= and the delete/change/yank verbs. Uppercase appends, as
vim does, and the unnamed register is still filled by every yank whatever
register was named. Not done: =:registers=, the numbered =0=–=9= ring, the
read-only =%= / =:= / =.= registers, and the clipboard registers =+= / =*= — which
want the clipboard that is still the first item on this list.
** DONE Macros — =q= to record, =@= to replay
=q<reg>= records, =q= stops, =@<reg>= replays and =@@= repeats. Keys are recorded,
not commands, so a replay re-runs the *decisions*. Nesting is capped at 20 —
=@a= that contains =@a= is a stack overflow rather than a hang, and nothing short
of running it can tell a legitimate nested macro from a runaway one.
** DONE Marks — =ma=, backtick-a
Distinct from the markers that now exist: those are the mechanism, this is the
vim-facing feature on top.
Backtick is the exact position, ='= the line, and both compose with an operator
(=d'a=). One marker per (buffer, letter), so a mark set in one file cannot be
read in another. Not done: backtick-backtick (wants a jump list), ='<= / ='>=
(wants a selection history), and the uppercase file-marks (want a marker table
that outlives a buffer).
** DONE Regex, and =:s= substitute — search is literal substring today
Search is =regex=, through a translation of vim's dialect: at vim's magic level
=(= is literal text and =\(= is a group, exactly backwards from PCRE, so the
backslash is swapped on =(){}|+?= and =\<=/=\>= become =\b=. =:s/pat/rep/=, =:%s= and
=:'<,'>s= (which =:= in visual mode types for you), with the =g= and =i= flags. The
whole substitution is one =Checkpoint= and one splice, so =u= reverses a =:%s= in
one press. The ceiling is written down at =vim_regex=: =\zs=, =\ze=, =\{-}=, =\%(=
and the =\v= magic levels all fail to compile rather than mean something else.
** DONE Incremental search — =/= should move as you type
The cursor follows the match on every keystroke, a pattern that stops matching
falls back to the origin, Escape restores it and RET commits where the preview
was — not one match further on. =PromptKind::previews= is the flag; the prompt
already reported its keystrokes, it just had nothing to say about a search.
** DONE Wide characters
=char_cells= (=unicode-width=, already in the tree because =alacritty_terminal=
measures its grid with it) is now the only thing with an opinion, and it turned
out to be a *smaller* change than it looked: a character occupying several cells
is exactly what a tab already was, so =expand_line= gives 漢 and 😀 a glyph cell
plus a blank continuation cell attributed to the same source character, and a
combining mark no cell at all. Everything downstream — =visual_col=, the
selection runs, wrapping, the cursor — was already written against cells and
needed nothing. The block cursor is as wide as the character under it.
Chrome measures in cells too, so a CJK candidate no longer overruns its box.

Offsets stay *characters* everywhere they cross into core: =(column)= counts
characters and a display column is not reachable from Lisp, because nothing in
Lisp draws. Left open: a wide character straddling the wrap point is cut rather
than moved down (Emacs moves it), and a control character draws as nothing
rather than as =^G=.
** DONE Backups — config keeps 20 versions, and so does zemacs now
Auto-save was already *done*: every modified buffer is copied to
=~/.zemacs.d/auto-save/#!mangled!path#= every 30 s, the copy is deleted on
a real save, and opening a file whose copy is newer says so. Numbered backups
of the previous *saved* version were the separate half, and now exist:
=~/.zemacs.d/backup/#!mangled!path#.~N~=, same mangling, capped at 20.

The other half of the same entry, and the more important one: *the write itself
could tear.* =fs::write= truncates and then fills, so a crash in between left a
file that was neither version — and auto-save does not cover that, because what
it copies aside is the buffer and what just became rubble is the file. Saving is
now write-to-sibling-temp, =sync_all=, =rename=, which reduces the outcomes to
"the old file" or "the new file". Symlinks are followed rather than replaced
(=~/.zshrc= is a link into a dotfiles repo on most machines) and the mode bits
are re-applied to the temp file, or every save of a shell script would quietly
take its =+x= off.

Two ceilings named in the code rather than closed: the directory entry is not
fsync'd after the rename, so a power cut can still lose a whole save (never half
of one); and =rename= breaks a hard link where Emacs would copy.
** DONE =:w= asks before overwriting a file that changed underneath
=Buffer::visited= is Emacs' =visited-file-modtime= — the file's stamp as of the
last read or write *by that buffer*, set by the app in the three places a buffer
comes into sync with disk (open, save, revert) because core cannot stat. =:w=
compares it and asks "changed on disk — save anyway?" when it moved.

Only for the file the buffer is actually visiting: =:w somewhere-else= is a
save-as, and the stamp on record describes the original. A bare =touch= is not a
false alarm, because the auto-revert sweep re-takes the stamp when it finds the
*content* identical — the same comparison that already stopped =:w= reverting
the buffer that wrote the file.
** DONE Auto-revert on external change (=global-auto-revert-mode= is on)
Polled off =Instant= beside the auto-save timer, at Emacs' own
=auto-revert-interval= of five seconds — a notification crate is a dependency,
a thread and a per-platform backend for a question one =stat= answers, and
Emacs polls for this too. One =stat=; a read only when the stamp moved.

Three things it will not do. A *modified* buffer is never reverted — it says
so once per external change and leaves your text alone. A =:w= does not revert
the buffer that wrote the file, because the text is compared and not just the
timestamp (which also makes a bare =touch= a no-op). And point is restored by
*line and column* rather than by offset, so text inserted above the cursor does
not drag it off the line you were reading.

The first of those is one half of an event whose other half is now the save
prompt above: the sweep says "changed on disk — not reverted" and deliberately
leaves the buffer's stamp stale, and =:w= is what asks about it.

ponytail: the live buffer only — every mutator core exposes goes through
=editor.buffer=, so a background buffer reverts within five seconds of you
switching to it rather than before. The upgrade is an
=EditorCommand::Revert(BufferId)=. Saving *over* a file that changed underneath
is still allowed and still silent; that is Emacs' "has changed since visited;
save anyway?" and it belongs with the confirmation flow the destructive git
verbs are waiting on.
** DONE =M-x= with arguments — it calls =(name)= and so offers zero-arg only
=M-x= still calls =(name)=, and that turned out to be the thing to leave alone. The
answer was already in the tree, written by hand: =load-theme= took its argument
=&optional= and *asked* when it was missing, which is what Emacs' =load-theme= does
and what made it the one argument-taking command you could reach. Generalising
that one line is the whole feature — =(interactive NAME SPEC...)= in
=runtime/library.lisp= replaces the symbol's function with a wrapper that
dispatches on whether it was given any arguments, and asks for the rest.

Nothing in Rust changed, and that is the result worth recording rather than the
feature. Three designs were tried against core first — arguments typed on the
=M-x= line, a =(%run-command "name")= dispatcher, a candidate list that carried
arity — and each of them wanted core to know something about Lisp. The wrapper
wants nothing from core at all, which is also why a *key binding* to a declared
command asks: both arrive as =(name)=, so there was never a second path to teach.

Two things fell out that were not obvious from the entry:

- =refresh-commands= needed one clause, not a rewrite. A declared command is
  offered because =(get sym 'interactive)= says so — asked as a property rather
  than by re-introspecting, since the wrapper's lambda list is =(&rest args)= and
  whether ECL describes a closure it did not compile is not a thing to bet the
  =M-x= list on.
- =*hidden-commands*= shrank by exactly one entry, and the entry says why that is
  the honest number: everything else on that list is a *reader* — =theme-names=,
  =buffer-lines=, =point-marker= — which is zero-argument and useless by hand for
  reasons arity was never the cause of. =set-language= was the only name hidden
  because its zero-argument call *meant* something wrong, and asking is the fix.

Now reachable, none of which could be run before: =set-scale=, =set-language=,
=lsp-register-server= (two prompts), and =load-theme= from a key as well as from
=M-x=. =set-font-size= deliberately stays unreachable — it is the primitive under
=set-scale= and sets the size without updating =*font-size*=, so running it by hand

(=SPC m p=), =parinfer-indent-buffer= (=SPC m P=), and the two that make it feel
like parinfer rather than a formatter: =parinfer-shift-right= / =-left= (=M-]= /
=M-[=) move the line by =tab-width= and let the parentheses follow, in *one*
=replace-region= so there is no window in which the form is unbalanced.

It refuses on a closing parenthesis with nothing open, because that means the
scan and the reader disagree and moving parens on a disagreement is how a
structural editor eats a file. A trailing surplus one is absorbed instead —
that is parinfer's bargain, and it is written down.

*What is not done: paren mode and smart mode.* Paren mode is
=lisp-indent-defun= plus a paren-trail tracker that must preserve edits made
inside the trail; smart mode needs to know *what changed*. That delta now exists
— =(after-edit-hook START OLD-END NEW-END TEXT)= — so this objection is retired
and the last one below is not, which is the one that was decisive anyway.
Half-building either gives a command
that reformats correctly nine times and eats a form on the tenth.

*And it is a command rather than a per-edit hook, deliberately.* Four reasons,
the last decisive: the hook carries no delta, so every keystroke would mean a
full rescan to find out whether an indentation moved; the rewrite is itself a
change and re-fires the hook; the rewrite is one =replace-region= over a whole
form, so undo would take back a paragraph per keystroke; and Lisp here is *not
synchronous with the command loop*, so the rewrite lands a queue turn after the
keystroke that provoked it and would silently discard whatever you typed in
between. Emacs' parinfer is safe from the last one only because elisp freezes
the editor while it runs, and that trade is the whole reason zemacs is not
elisp.

** DONE Group N edits into one undo step — *closed by argument, not by a

| buffer | full | before | after |
|--------+---------+---------+---------|
| 280 KB | 21 ms | 9.4 ms | 3.7 ms |

| 4.5 MB | 344 ms | 150.7 ms | 16.8 ms |

~9× at the top end; one keystroke re-queries about 67 KB of a 4.5 MB file.

*The soundness work was the job*, because =changed_ranges= bounds where the
*tree* differs and not where the *colour* does. Two holes, both real:

- A match is a pure function of the subtree it is rooted at, but
  =changed_ranges= reports only the non-identical parts of a changed subtree.
  Typing a statement above a Python docstring leaves the string byte-identical
  and unreported while =(module . (expression_statement (string)))= stops
  matching it. The changed set is widened to whole top-level items plus one
  either side; removing either the widening or the slack fails the test.
- *The walk lies under error recovery.* It skips any pair of subtrees agreeing
  on symbol, size, parse state and error cost — and two *different* error
  subtrees can agree on all four. A fuzz found a deletion in broken Python that
  re-lexed a =from= a thousand bytes away from identifier to keyword with
  nothing in the changed set to say so. An item that did not parse cleanly is
  now trusted only where it is being re-queried anyway. Typing inside the item
  you have just broken — which is where the error is while anyone is typing —
  stays on the fast path.

Evidence beyond the suite: 40 320 random edits over 7 languages, *zero*
disagreements against a full query of the same tree. Eight edits disagreed with
a *fresh* parse, and all eight already disagreed before this change —
tree-sitter's error recovery is path-dependent, so an edited tree can
legitimately differ from a from-scratch one. That is why the committed fuzz
compares against the session's own tree.

Two ceilings, both noted in code: a file whose top level is *one* item (a JSON
document, a file that is one =mod=) re-queries everything and saves only the
parse; and an error left elsewhere in the file costs a full query, which is
exactly what every keystroke used to cost and never worse.

At 4.5 MB the residual is parse 2.9 ms / requery 6.6 ms / span copy and char
conversion 8.5 ms — the O(file) bookkeeping now dominates, and its upgrade
(hand the caller the changed run rather than the whole list) is a change to
core's and the renderer's side of the boundary rather than to =crates/syntax=.

* THE COMMON LISP MIGRATION
The goal: as much as possible in Lisp, performance-critical work in Rust.
The boundary that makes that safe —

- *Rust, touched per frame or per character*: rope and edit primitives,
  rendering, tree-sitter, terminal emulation, process spawn, file IO.
- *Lisp, touched once per command*: everything a keystroke triggers.

That is Emacs' own line, and it is why elisp being slow never mattered.

** The strip answers the mouse                                       :done:

   strip and hands Lisp the **template** it was drawn from plus the text it

   `*mathsync-keep*' is the way back.

** The microphone belongs to the bundle                              :done:

   =scripts/bundle.sh= declares `NSMicrophoneUsageDescription' and
   `NSSpeechRecognitionUsageDescription'. A child spawned in `:term' inherits
   zemacs's TCC identity, and macOS denies a recording attempt *outright* when
   the bundle has no usage string — no prompt, no dialog, which is why it looks
   like the tool being broken rather than a missing plist key.

   Not verified here, and it cannot be: TCC is a system database and a test
   process has no window. Re-bundle, and if a denial was already cached under
   the old plist, `tccutil reset Microphone org.zemacs.zemacs' forgets it.

** An equation is set at the size of the text around it              :done:

   `latex-preview' takes a scale — a multiple of the body em, carried as the
   hundredths this boundary already carries `overlay-scale' and `%image-file'
   in — and it reaches dvipng as a **dpi**, so a heading's equation is typeset
   large rather than being a small one scaled up.

   Two factors and they multiply. Where it is: `%org-latex-scale' counts the
   leading stars of the line and sizes the fragment by org-modern's own
   `*org-modern-heading-scale*', so a config that resizes its headings resizes
   the mathematics in them. `**bold**' at the start of a line is not a level-2
   heading — stars make one only with a space after them — and without that
   test every equation in a paragraph opening with emphasis came out oversized.
   What it is: `latex-fragments' has always answered `display' and every caller
   ignored it; `\[…\]' now gets `*org-latex-display-scale*', 1.25, because it
   has a line of its own and is what the paragraph is about.

   Not done: =org-frozen.lisp= builds its own page and still previews at body
   size, so an equation in a frozen heading is smaller than the same equation
   in the live buffer. Its `%org-frozen-latex-piece' would have to carry a size
   down through the layout.

** A preview came back on leaving the *line*, not the fragment       :done:

   Which is the whole of "previews kind of inconsistently". `$a$ and $b$' is two
   equations on one line: stepping off the first onto the word between them left
   the line unchanged, so nothing re-typeset it and it stayed spelled out until
   you pressed `j'.

   `org-latex-reveal-at-point' remembers the range it opened rather than the
   line it was on — `overlays-in' already answers (ID BEG END), so it costs no
   second query — and the re-render fires the moment point is outside it. The
   line flag stays for *edits* and clears the range one: typing moves the
   fragment's end, and a stale end reads as having walked out, which would run
   LaTeX in the middle of a word.

** Wrapping is a fact about the document                             :done:

   `Buffer::line_overflow', stamped by `SetLineOverflow' exactly as
   `Buffer::text_width' is, and read through one new `zemacs_core::wraps'.

   The setting was the editor's and there is one of it, so the *unfocused* frame
   went on drawing a buffer under the focused buffer's rules. Clicking into a
   code frame un-wrapped the prose in the frame beside it — a window nobody had
   touched reflowed — and the same thing happened between two panes of a split.

   It was three bugs, not one, because three loops asked the question:
   `visible_lines' counted the rows, the draw loop drew them, and `offset_at'
   answered where a click landed. So a click in an org pane while a `.rs' was
   focused also landed on the wrong line. `Editor::visual_lines' reads it too,
   so `j' and `k' count screen rows in the right buffer as well.

** The wheel crosses rows, `scroll' counts lines                     :done:

   The other half of "the mouse doesn't work super well in org buffers", and org
   is where it bites because org is the mode that wraps: a paragraph is one
   buffer line and eight rows on screen, so a notch that moved three lines in a
   code file threw three paragraphs past you in prose. A 1.5× heading and a
   display equation do the same thing for the same reason.

   `Renderer::scroll_step' converts the notch at the one place it enters, so
   `Editor::scroll' stays a line everywhere and the *gesture* is in rows. A
   buffer with no wrapping and nothing typeset takes the identity fast path, so
   the wheel feels exactly as it did in code.

   ponytail: a line taller than one notch is stepped over or into, never
   through. The upgrade is `(line, row)' in `Editor::scroll', which is a change
   to every clamp in core.

** A picture you drag or paste is a figure                            :done:

   Both gestures end at `%org-insert-image', which writes an org link and draws
   it, so however a figure arrives it means the same thing. What lands in the
   buffer is text you could have typed — the file stays where it is, and the
   document opened anywhere else still says `[[file:...]]'. Nothing here invents
   a binary attachment.

   The link is relative when the file is inside the document's own folder, which
   is what survives that folder being moved or checked in, and `~/'-abbreviated
   otherwise. It goes on its own line because that is org's rule for what a
   figure is and this runtime's rule for what it will draw, and the whole
   insertion is one `insert-at' — so `u' takes the picture and its line away
   together.

   *Dropping* already had an arm and it did the wrong thing: `Event::DropFile'
   fell through to `open_file', so dragging a PNG onto a document opened the PNG
   as a text buffer. It now asks `%file-dropped', but only when the live buffer
   is org — which is the one part of the question core can answer for itself.
   Which files are pictures stays `*org-image-file-types*', in Lisp, where it
   already was; anything that is not one is still a file you meant to open.

   *Pasting* is `EditorCommand::ClipboardImage', a request in `ListFonts'' shape
   and for its reason: core does no IO and has no clipboard, and the layer that
   owns a window is the only one that can reach a pasteboard. The app writes the
   picture to `~/.zemacs.d/images/' — named by content, so pasting the same
   screenshot twice is one file — and answers by calling `%clipboard-image'.
   `M-v' (which is ⌘V here) and `SPC m v'. The reply checks the mode again,
   because the buffer can change across a round trip through another thread.

   And JPEG, which the gesture forced. `crates/figure' was PNG and SVG on the
   argument that "a photograph is not a figure in a textbook" — true while a
   figure arrived by being typed as a link, and false the moment you can drag
   one in, because what you drag is a photograph. The ceiling note predicted the
   fix exactly: one manifest line for `zune-jpeg', which `resvg' already builds,
   and one arm. The two raster decoders are chosen by *magic number* rather than
   by extension, so a `.png' that something re-saved as a JPEG still reads.

   Still missing: `.webp', which is a real decoder crate rather than a free one.

** Modus headings wore the title's colour                            :done:

   `heading-1' took Modus' `fg-heading-0' — which is what a `#+title' is set in,
   not a heading — on the argument, written in the file, that zemacs had one
   heading size so hue was the only thing left to rank three levels with.

   That argument was never true here. `*org-modern-heading-scale*' has set level
   1 at 1.5x and level 2 at 1.25x since the commit *before* the one that added
   these themes. And it cost twice over, because `fg-heading-0' is also exactly
   this theme's `type' — so a heading in a document with code in it read as a
   type name, which is the "doesn't quite fit" you can see and cannot name.

   Level 1 is `fg-main' now, as Modus spells it, in all three files. Bold at
   1.5x says top-level far more plainly than a hue can, which is why Modus
   spells it that way. Levels 2 and 3 were already right and are untouched.

** The `…' was a fold marker, and there was nothing folded              :done:

   `%org-latex-draw' set `:fold' on *every* preview overlay, on the argument —
   written in the comment beside it — that a one-line fragment has no line after
   its first and so folding it is a no-op. That is true and it was not the whole
   story: a fold is what the renderer draws its `…' for, so every line holding
   an inline `$x^2$' grew an ellipsis on the end claiming there was text behind
   it. There was none. The flag was being used to claim rows the fragment did
   not have.

   Two halves, because both were wrong. Lisp only folds a fragment whose source
   actually contains a newline — a `\begin{align}', which is the case the flag
   exists for. And `fold_starts_in' — whose only caller is the marker, and whose
   whole question is "does this line get the indicator" — now says no for a fold
   carrying an `image': the rows it hid are the *source* of the picture drawn in
   their place, and the picture already says so. `fold_hiding' is untouched, so
   `j' still steps over them.

** `C-b' and `C-i' while typing                                      :done:

   `org-emphasis-bold' wraps the selection or opens an empty `**' with point
   between the stars — the empty half is what makes it a key you press *while*
   typing, since the tedious character is always the closing one. One
   `insert-at', so it is one undo step and no keystroke can land between the
   halves.

   Bound in the **insert** state and not in org's keymap, which is the one
   decision here: a mode binding applies in every state, and in Normal `C-b' is
   vim's page-up and `C-i' its jump-forward. Both are worth more than a second
   spelling of `SPC m b', which still exists and still says "no selection". A
   state binding is global, so the guard is in the command — and it costs
   nothing elsewhere, because an unbound Ctrl chord in Insert already did
   exactly nothing.
