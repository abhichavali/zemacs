#+TITLE: Reference
#+SUBTITLE: every primitive, reader and helper

Everything below lives in the =ZEMACS= package, and everything except the
=%=-prefixed internals is exported, so both =(point)= and =(zemacs:point)= read.
Anything the editor evaluates for you already has =*package*= bound to =ZEMACS=; a
file you =LOAD= yourself wants =(in-package :zemacs)= at the top.

The =%= prefix means "internal": =%query=, =%do=, =%save-file= and =%make-marker= are
reachable unqualified from inside =ZEMACS= (or as =zemacs::%do=), but they are not
exported and =refresh-commands= deliberately keeps them out of =M-x=.

* Conventions

- *Offsets are characters*, counted from 0, never bytes and never lines. The one
  exception is line *numbers*, which are 1-based, matching what =(line-number)=
  reports and what the gutter draws.
- *Failure is =NIL=*, never an error. An unknown reader answers =NIL=; an unknown
  =%do= verb reports in the status line. A config written against a newer zemacs
  degrades instead of failing to load.
- *Out-of-range arguments are clamped, not rejected.* =(buffer-substring 0
  most-positive-fixnum)= means "to the end", and a reversed pair is put in order.
- *Writers return =NIL=* unless the table says otherwise.
- Three mechanisms are marked in the tables, because they behave differently:
  =P= a C primitive, =R= a reader (answers from the live editor), =H= a Lisp helper
  built out of the other two. =A= marks the commands that need the app layer and
  therefore land a frame later — see [[file:threading.org][threading.org]].

* Position

| Form                          |   | Answers                                              |
|-------------------------------+---+------------------------------------------------------|
| =(point)=                       | R | Cursor offset.                                       |
| =(point-min)=                   | R | Always 0.                                            |
| =(point-max)=                   | R | Offset past the last character = character count.    |
| =(buffer-size)=                 | R | Same as =point-max=.                                   |
| =(line-number)=                 | R | 1-based line the cursor is on.                       |
| =(column)=                      | R | 0-based column, counted in *characters* — see below. |
| =(line-count)=                  | R | Number of lines, counting the empty one after a trailing newline: 3 for ="a\nb\n"=. |
| =(line-start &optional line)=   | R | Offset of the first character of =line= (1-based), or of the cursor's line. |
| =(line-end &optional line)=     | R | Offset just past the last character, *newline excluded*. |
| =(goto-char n)=                 | P | Move the cursor. Clamped to the buffer.              |
| =(goto-line n)=                 | H | Start of 1-based line =n=.                             |
| =(beginning-of-line)=           | H | =(goto-char (line-start))=                             |
| =(end-of-line)=                 | H | =(goto-char (line-end))=                               |

#+begin_src lisp
;; "alpha\nbeta\ngamma\n", cursor on line 2
(list (point) (line-number) (column))  ; => (8 2 2)
(line-start 2)                         ; => 6
(line-end 2)                           ; => 10
(line-string 9999)                     ; => ""  — clamped to the last line
#+end_src

*A column is a character, not a cell.* =(column)= counts characters, exactly as
=(point)= counts characters — every offset in this API does, because the document
is a rope of characters and nothing else would round-trip. The *screen* column is
a different quantity: =漢= is drawn two cells wide and a combining mark none, so on
a line of CJK the cursor is at column 3 and in screen cell 6. That conversion is
=crates/core/src/display.rs=, shared by the renderer and by =j= / =k= so the two
cannot disagree, and it is deliberately *not* reachable from Lisp — there is no
reader that answers in cells, because nothing in Lisp draws.

*Watch the Normal-mode clamp.* In Normal mode the cursor sits *on* a character,
never past the last one, so =goto-char= to =(line-end)= is pulled back by one. On
line 3 of the buffer above:

#+begin_src lisp
(goto-line 3)
(end-of-line)
(list (point) (line-end))              ; => (15 16)
#+end_src

That is the editor's rule, not a rounding error. In Insert mode there is no
clamp. Anything computing a range should use =(line-end)= and not =(point)= after
an =end-of-line=.

* Reading text

| Form                            |   | Answers                                        |
|---------------------------------+---+------------------------------------------------|
| =(buffer-string)=                 | R | The whole buffer.                              |
| =(buffer-substring beg end)=      | R | =[beg, end)=. Clamped and ordered.               |
| =(line-string &optional line)=    | R | One line, newline excluded.                    |
| =(buffer-lines)=                  | H | Every line as a list, newlines excluded, *without* the empty trailing one. |
| =(search-forward pattern &optional start)= | H | Offset of the first =pattern= at or after =start= (default point), or =NIL=. |
| =(search-backward pattern &optional start)= | H | Offset of the last =pattern= ending at or before =start=, or =NIL=. |

Search is *literal*. ECL ships no regexp engine, so =cl:search= is what there is.
Both helpers answer in character offsets even though the buffer arrives as UTF-8
bytes, so the result feeds straight into =goto-char=.

=buffer-lines= is the line-oriented starting point, and exists because a rope
counts the empty line after a trailing newline: =(line-count)= on ="a\nb\n"= is 3
and =(buffer-lines)= is =("a" "b")=. Anything iterating over lines wants the second.

#+begin_src lisp
(buffer-lines)                  ; => ("alpha" "beta" "gamma")
#+end_src

#+begin_src lisp
;; Jump to the next TODO, or say there isn't one.
(defun next-todo ()
  (let ((hit (search-forward "TODO" (1+ (point)))))
    (if hit (goto-char hit) (message "no more TODOs"))))
#+end_src

* Writing text

| Form                              |   | Effect                                          |
|-----------------------------------+---+-------------------------------------------------|
| =(insert text)=                     | P | Insert at point, moving it. One undo step.      |
| =(insert-at pos text)=              | H | Insert at =pos= without moving point. One undo step. |
| =(delete-region beg end)=           | P | Delete =[beg, end)=. Ordered and clamped. One undo step. |
| =(replace-region beg end text)=     | P | Delete then insert, *atomically*. One undo step. |
| =(delete-line &optional line)=      | H | Delete a whole line, newline included.          |
| =(replace-all from to)=             | H | Replace every occurrence. Answers how many. One undo step. |
| =(undo)= / =(redo)=                   | H | One step through this buffer's history.         |

=replace-region= is the atomic primitive the whole design points at. Anything
that must not be interrupted halfway is written as one call to it:

#+begin_src lisp
(defun surround-region (left right)
  "Wrap the selection in LEFT and RIGHT."
  (let ((r (region)))
    (if r
        (replace-region (car r) (cdr r)
                        (concatenate 'string left (region-text) right))
        (message "no selection"))))
#+end_src

=insert-at= is =replace-region= over an empty range, which is why it neither moves
point nor leaves a gap a keystroke could land in.

=replace-all= builds the entire new buffer text in Lisp and issues *one*
=replace-region=. It answers the number of replacements and leaves point where it
was (clamped):

#+begin_src lisp
(replace-all "foo" "bar")   ; => 7
#+end_src

Its one cost: replacing the whole buffer is a deletion that swallows every
marker, so none of them survives it — they collapse onto position 0, or onto
the end for one made with =advance=. If you hold markers, do a targeted
=replace-region= per hit instead and accept the extra undo steps.

* Markers

A char offset names a character only until the next edit. A marker names it
afterwards too, because every edit in the editor is a splice and every splice
adjusts the markers.

| Form                                 |   | Answers                                       |
|--------------------------------------+---+-----------------------------------------------|
| =(make-marker &optional pos advance)=  | H | A handle (an integer). =pos= defaults to point. |
| =(point-marker)=                       | H | =(make-marker)=.                                |
| =(marker-position m)=                  | R | Where it is now, or =NIL= if deleted or in another buffer. |
| =(set-marker m pos)=                   | P | Move it.                                      |
| =(delete-marker m)=                    | P | Drop it.                                      |
| =(goto-marker m)=                       | H | Move point there; answers the position, or =NIL=. |
| =(save-excursion &body body)=          | H | Run =body=, then put point back. Answers =body='s value. |

=advance= is the insertion type: with =NIL= (the default, as in Emacs) the marker
*stays* when text is inserted exactly at it; with anything else it rides along.

A handle answers =NIL= once it is deleted, or while the buffer it belongs to is
not the live one — so =(when (marker-position m) ...)= is the idiom, the same
shape as =region=. Holding one too long is a mistake a config makes, never one it
can crash on.

#+begin_src lisp
(let ((m (progn (goto-char 6) (point-marker))))
  (goto-char 0)
  (insert "XY")
  (marker-position m))     ; => 8 — still the same word
#+end_src

=save-excursion= is built on a marker rather than an integer, so an edit *in front
of* point inside the body still puts the cursor back on the same character:

#+begin_src lisp
(save-excursion
  (goto-char 0)
  (insert ";; generated\n"))
;; point is back where it was, on the same character
#+end_src

Two caveats, both from the module's own docs:

- =(make-marker)= puts a marker *at point* rather than nowhere. There is no
  positionless state, so Emacs' =(make-marker)= then =(set-marker m p)= is
  =(make-marker p)= here.
- The insertion type is fixed at creation; there is no
  =set-marker-insertion-type=.
- Undo restores a whole snapshot rather than replaying edits backwards, so a
  marker beyond the restored end is *clamped* onto it rather than restored
  exactly. It is never outside the document, which is the invariant a marker
  owes its holder.

* Overlays

A marker names a position across an edit. An overlay names a *range* across one,
and carries something with it — a colour, a substituted string, an image, a type
size, or any Lisp object at all. It is a marker pair plus a property list, which
is exactly how it is built.

It is also the whole of the drawing API. There is no second vocabulary for
"make this look different": a mode that wants larger headings, a bold run, a
quoted block or a folded subtree says all four with =overlay-put=, and the
renderer knows none of those words.

| Form                            |   | Answers                                                  |
|---------------------------------+---+----------------------------------------------------------|
| =(make-overlay beg end)=          | P | A handle (an integer), or =NIL= for an empty range.         |
| =(overlay-put ov prop value)=     | H | Sets a property. Answers =value=.                          |
| =(overlay-get ov prop)=           | H | Reads one back, or =NIL=.                                  |
| =(overlay-position ov)=           | R | =(START . END)=, or =NIL= if it is gone or in another buffer. |
| =(overlay-start ov)=              | H | =(car (overlay-position ov))=                              |
| =(overlay-end ov)=                | H | =(cdr (overlay-position ov))=                              |
| =(overlays-in beg end)=           | R | =(ID START END)= per overlay *overlapping* the range, oldest first. |
| =(overlays-at pos)=               | H | =(overlays-in pos (1+ pos))=                               |
| =(delete-overlay ov)=             | H | Drops it and its properties.                             |
| =(remove-overlays &optional beg end)= | H | Drops *every* overlay overlapping the range. Whole buffer by default. |

There are *no text properties*. Emacs has both because properties live in the
buffer's string data and therefore survive a copy into the kill ring; a rope of
characters is what makes every offset here a character index, and threading a
plist through it would give that up to buy an inheritance rule most configs turn
off. One mechanism, and this is it.

** The properties the renderer draws

Two groups, and the split is worth knowing: most of them are about the *cells* a
range covers, and three are about the *lines* it touches, whole.

| Property         | Value                        | Effect                                    |
|------------------+------------------------------+-------------------------------------------|
| =face=             | a name from =(face-list)=      | Foreground of the covered text.           |
| =background=       | a name from =(face-list)=      | Background of the covered cells.          |
| =display=          | a string                     | Drawn *instead of* the covered text.      |
| =image=            | =latex-preview= or =image-file= | Drawn instead of the covered text, as a bitmap. |
| =weight=           | ='bold=, ='normal=              | Real weight, not a colour.                |
| =slant=            | ='italic=, ='normal=            | Real slant.                               |
| =scale=            | a number, =1.0= being body     | Type size — *for the whole line*. See below. |
| =line-background=  | a name from =(face-list)=      | A band across the whole pane, behind every line the range touches. |
| =line-prefix=      | a string                     | Drawn in the left margin of every row of those lines, text pushed right by its width. |
| =fold=             | =T= or =NIL=                     | The lines *after* the first stop occupying rows at all. |

=NIL= clears any of them. A colour is a *face name*, not an =(R G B)= — the theme
already owns that vocabulary, so an overlay recolours itself when a theme is
loaded, and an overlay wanting a colour no face has must =set-syntax-color= a
spare face first.

Priority, where two things claim the same cell:

1. an overlay's =face= / =background= beats the syntax highlight;
2. among overlapping overlays the *most recently made* wins, and per attribute —
   one that sets only a background leaves an earlier one's foreground alone;
3. the selection and the cursor beat both. They are claims about the editor
   rather than about the text, and nothing a config paints may hide them.

Overlapping =display= substitutions are not composed: the one that starts first
wins and the rest are ignored.

=weight= and =slant= are three-valued, and the middle value earns its place:
='normal= is a claim, and overrides an overlay underneath; =NIL= is the absence of
one, and leaves that overlay's alone.

** Type size

=scale= is a multiple of the body size, so text follows =font-size= and a heading
follows the text: =C-+= enlarges the document rather than closing the gap between
its parts.

Two things about it are not obvious and both are deliberate.

*It scales the line, not the run.* A scaled cell is wider as well as taller, and
every piece of layout downstream — where a line wraps, which column the cursor is
in, which character a click lands on — counts in whole cells of one width. So the
*widest* scale claimed by any overlay touching a line sets that whole line's
type, rather than a run carrying its own advance. That is what a heading wants
anyway, and it is what lets =org-modern= scale a heading with the overlay it
already puts on the stars. ponytail: =*this* word bigger= is therefore not
expressible. =weight= and =slant= *are* per-run, because they change no metric.

*The size is snapped to one of four steps* — =1.0=, =1.25=, =1.5=, =2.0= — and a
request lands on the nearest. That is not a rounding accident: a font face plus a
texture per character it has drawn is what a size costs, so the steps are the
renderer's glyph cache bound made visible in the vocabulary rather than hidden in
an eviction policy. Ask for =1.4= and you get the =1.5= face.

A scaled line claims whole extra rows — =ceil(scale)= of them per wrapped row —
which is the same mechanism an inline image already used, and is what keeps
=scroll=, the gutter and the click map counting whole rows. The type sits at the
*bottom* of that block, so the slack lands above the line, which is where a
heading wants its air.

#+begin_src lisp
;; A quoted block drawn as a block rather than as coloured characters.
(let ((ov (make-overlay beg end)))
  (overlay-put ov 'line-background "code")
  (overlay-put ov 'line-prefix "▎ ")
  (overlay-put ov 'face "comment"))            ; ...which is also the bar's colour
#+end_src

** Folding

=fold= is the odd one out and worth its own paragraph: the others swap cells for
other cells or change how big they are, and this makes *rows stop existing*. Every line after the
overlay's first, up to its end, is skipped by the renderer and stepped over by
=j= and =k= — one predicate answers for both, because a line the frame does not
draw and a line the cursor may land on have to be the same set or point
disappears. The overlay's own first line stays drawn and gets a =…= after its
text, which is what you unfold from.

It is an overlay and gets everything an overlay gets: it slides when you type
above it, it dies when its text is deleted, =delete-overlay= opens it, and undo
clamps it back into the document.

| Form                     |   | Effect                                                |
|--------------------------+---+-------------------------------------------------------|
| =(fold-region beg end)=    | H | Hide every line after =beg='s, through =end='s. Answers the overlay. |
| =(folds-in beg end)=       | H | Handles of every fold overlapping the range, oldest first. |
| =(folded-p &optional pos)= | H | The innermost fold covering =pos= (default point), or =NIL=. |
| =(unfold-region beg end)=  | H | Delete every fold overlapping the range. Answers how many. |
| =(unfold-all)=             | H | Open every fold in the buffer.                        |

Those five are the whole mechanism, and *nothing in them knows what a subtree
is*. That is the policy, and it lives in =runtime/modes/org-fold.lisp=:

| Form                        |   | Effect                                              |
|-----------------------------+---+-----------------------------------------------------|
| =(fold-dwim)=                 | H | Toggle the selection, or the mode's subtree under point. =z a= |
| =(fold-all)=                  | H | Fold every foldable range in the buffer. =z M=        |
| =(fold-open-all)=             | H | Open them all. =z R=                                  |
| =*fold-subtree-functions*=    |   | Major mode -> a function answering =(BEG . END)= under point. |
| =*fold-all-functions*=        |   | Major mode -> a function answering every =(BEG . END)=. |

Teaching another mode to fold is one entry in each alist and one function; there
is nothing to add in Rust, because Rust has no opinion about what a subtree is.

#+begin_src lisp
;; Fold a `defun' in a Lisp buffer, over the sexp motion lisp-mode already has.
(defun lisp-defun-at-point ()
  (save-excursion
    (let ((beg (progn (beginning-of-defun) (point))))
      (cons beg (progn (forward-sexp) (point))))))

(push (cons "lisp-mode" 'lisp-defun-at-point) *fold-subtree-functions*)
#+end_src

ponytail: folding is two-state, not org's three — a headline is closed or open,
and opening one opens everything under it (org's =SUBTREE=, never =CHILDREN=).
The upgrade is a third case in =fold-dwim= and a per-headline state table, all of
it in Lisp.

** Every other property

Anything. A property the renderer has never heard of is stored *in the image*, in
=*overlay-properties*=, so its value may be a closure, a structure, a hash table —
whatever an avy hint, a copilot completion or a flymake diagnostic wants to hang
off the range. It never crosses into Rust, so it never has to survive being
printed and re-read.

#+begin_src lisp
(let ((ov (make-overlay (region-beginning) (region-end))))
  (overlay-put ov 'face "keyword")
  (overlay-put ov 'jump-to (point-marker))       ; only Lisp sees this
  (overlay-get ov :jump-to))                     ; 'jump-to and :jump-to are one key
#+end_src

Property names are compared as *keywords*, so =face=, =:face= and a symbol read in
another package are the same property.

** Two things to know before holding one

- An overlay whose text is deleted is *deleted with it*. Emacs would keep a
  zero-width overlay; here every payload is about the text underneath, and a
  =display= string over no text is a ghost. =(overlay-position ov)= answering =NIL= is
  how you find out, the same shape =marker-position= has.
- Text typed at the *front* of an overlay lands inside it; text typed at the
  *back* lands outside. Those are Emacs' defaults and they are fixed — there is no
  =front-advance= / =rear-advance= pair.

* LaTeX previews

| Form                    |   | Answers                                                    |
|-------------------------+---+------------------------------------------------------------|
| =(latex-fragments)=       | R | =(START END DISPLAY-P)= per fragment in the buffer, in order. |
| =(latex-preview source)=  | P | An image handle for an =image= overlay property, or =NIL=.     |

Together with overlays these are the whole of =org-latex-preview=, which is
written in Lisp in =runtime/init.lisp= and is worth reading as the shape of a
feature here: Rust finds the fragments and rasterises one, Lisp decides which
ones and what to do with the result.

=latex-fragments= is org's notion of a fragment — =$…$=, =\(…\)=, =$$…$$=, =\[…\]= and
=\begin{env}…\end{env}= — found in prose only, so a =$= inside a =#+begin_src= block
is a dollar sign. =DISPLAY-P= is =T= for the ones that want a line of their own.

=latex-preview= shells out to =latex= and =dvipng=, which means:

- it is *slow the first time* — a few hundred milliseconds — and instant
  afterwards, from a cache on disk that survives a restart;
- it blocks *the image*, not the editor. Frames keep being drawn and keystrokes
  keep being handled while a screenful of equations is typeset, which is the
  whole reason Lisp has a thread of its own;
- it answers =NIL= and puts the reason in the status line when TeX is not
  installed or the fragment does not compile;
- the handle is derived from the fragment, the size and the colour, so previewing
  the same fragment twice costs nothing at all.

* Highlighting a string

| Form                    |   | Answers                                              |
|-------------------------+---+------------------------------------------------------|
| =(highlight lang text)=   | P | =(START END FACE)= per run, in char offsets, sorted. |

A **pure function**: it reads no buffer, takes no lock, and parses whatever you
hand it. =FACE= is a name from =(face-list)=, so a run goes straight onto an overlay:

#+begin_src lisp
(dolist (run (highlight "python" body))
  (destructuring-bind (a b face) run
    (overlay-put (make-overlay (+ beg a) (+ beg b)) 'face face)))
#+end_src

It exists because a buffer has *one* language and sometimes a piece of it is
written in another. Org is the case that wanted it: a =#+begin_src python= block
lives in a buffer the highlighting thread is colouring as org — which has no
tree-sitter grammar at all — so the block can only be coloured by asking for it.
=runtime/modes/org-frozen.lisp= is the customer and =org-frozen-mode= is what it
buys. Nothing about the primitive is about org: "colour this string as that
language" is what a markdown fence, a docstring or a diff view would each want.

Two things to get right when calling it:

- =LANG= is a *tree-sitter* language id, not a babel name. =(languages)= is the
  list; =emacs-lisp= is =lisp= and =py= is =python=, and a name no grammar answers to
  simply gets an empty list back — the same answer a parse failure gives, so
  there is one case to handle and not three.
- =TEXT= must be real characters. =buffer-substring= answers one character per
  UTF-8 *byte* — the convention =docs/threading.org= writes up and the reason
  =%char-index= exists — and handing that over unchanged makes the parser count a
  longer string than the buffer holds, so every run after the first accented
  character lands a byte or two to the right. =%org-frozen-text= in
  =runtime/modes/org-frozen.lisp= is the decoder, and the note above it is where
  the whole story is written down.

The image is rasterised to match the text it sits in and placed against the
*baseline*, so =$x_1$= hangs below the line the way a descender does. A fragment
taller than one line gets one: the line it starts on grows to as many display
rows as the image needs, so a display equation claims space upward from its own
baseline instead of painting over the text below. A fragment spanning several
source lines already owns a blank row for each of them and is charged only the
shortfall, so =\begin{equation}= looks exactly as it did.

** Previewing without being asked

An org buffer typesets itself. Two triggers, both policy in =runtime/init.lisp=
and both chosen to keep a =latex= run off the keystroke path:

- *entering =org-mode== — the buffer arrives typeset. Cold, that is one render per
  fragment while the editor keeps taking your keystrokes; warm, it is the cache.
- *leaving the line you edited* — =after-change-hook= records only which line
  changed, and =point-moved-hook= does the work once point is on a different one.
  So typing costs one integer comparison per keystroke, a pass happens once per
  line you edit rather than once per character, and =$\alph= is never handed to
  TeX half-typed.

Only fragments with no preview overlay are rendered, and never the one point is
inside. A pass that cannot render anything sets =*org-latex-auto*= to =NIL= and says
so once — a machine with no TeX should not print the same error per equation —
and =M-x org-latex-preview= turns it back on, since asking by hand is how you say
you have installed it.

* Figures

| Form                        |   | Answers                                                |
|-----------------------------+---+--------------------------------------------------------|
| =(image-file path &optional width)= | P | An image handle for an =image= overlay property, or =NIL=. |

The other producer of an =image= handle, and deliberately the same contract as
=latex-preview=: pixels in the editor under an id, =NIL= with the reason already in
the status line, and an id derived from exactly what decided the pixels — here
the path, the file's length and mtime, and the width — so drawing an unchanged
figure again is a lookup and a rewritten one is genuinely re-read.

- *SVG and PNG.* =.svg=, =.svgz= and =.png=. SVG goes through =resvg=, which is pure
  Rust, so a figure costs no system dependency; PNG goes through the decoder the
  LaTeX pipeline already builds.
- =WIDTH= is *in ems* and is a **maximum** — nothing is ever scaled up. Ems and
  not pixels because the device pixel is something only the renderer knows: a
  width computed in the image from =(font-size)= comes out half-size on a Retina
  display. =NIL= means "as authored".
- A vector file is rasterised at the display's scale factor before the maximum
  applies, which is the same correction =latex-preview= makes with its dpi.

Together with overlays this is the whole of =org-inline-images= in
=runtime/modes/org-modern.lisp=: a =[[file:fig-1.svg]]= link alone on its line gets
an overlay carrying the handle, and the renderer grows the line to fit the
bitmap exactly as it does for a display equation. =SPC m f= redraws, =SPC m F=
clears, and entering =org-mode= draws what has none yet.

* Following a link

| Form                   |   | Does                                                     |
|------------------------+---+----------------------------------------------------------|
| =(org-open-at-point)=    | C | Follows the link under point. =RET= in an org buffer.      |

=*org-link-open-functions*= is the policy table: a scheme, and the function that
follows it. =id:= jumps to the heading carrying that =:ID:= (or =:CUSTOM_ID:=),
=file:= opens the file relative to *this* file's directory, and =http:=, =https:=
and =mailto:= go to the desktop's own opener. A target with no scheme is org's
fuzzy link: =*Heading= is a headline, =#name= is a custom id, and anything else is
a file if one is there and a search if it is not.

Adding =doi:= or =roam:= is a line in that table and a function. Nothing in Rust
knows what a link is.

* org as a printed page

=org-frozen-mode= renders an org file instead of editing it. =SPC m z= toggles it
either way, from an org buffer or from a frozen one.

| Form                    |   | Does                                                     |
|-------------------------+---+----------------------------------------------------------|
| =(org-frozen-mode)=       | C | Freeze the live buffer. Derives from =org-mode=.           |
| =(org-frozen-toggle)=     | C | ...and back again. =SPC m z=                               |
| =(org-frozen-refresh)=    | C | Redraw the page. =SPC m m=                                 |
| =(org-frozen-clear)=      | C | Take the rendering off, leaving the mode on.             |
| =(org-frozen-cycle)=      | C | Org's heading cycle, machinery intact. =TAB=               |

It is =org-modern= *plus more, minus the reveal*: entering it runs =org-mode='s own
body first, so the bullets, the emphasis, the LaTeX previews and the inline
figures are all that file's and are not redone. What it adds:

- **Machinery stops occupying rows.** Property drawers, =#+keyword:= lines,
  =#+begin_…=/=#+end_…= delimiters and =#= comments are folded — not dimmed, not
  replaced by a glyph. =j= steps over them too, because [[*Folding][=fold_hiding=]] is the one
  predicate the renderer and the cursor both ask.
- **=#+TITLE:= is typeset**, at twice the body size, rather than hidden. It has to
  be: a fold hides the lines *after* its own, so line 0 is out of reach of every
  fold there can ever be, and a title is the likeliest thing to be on it.
- **A source block is a listing** — a =line-background= band, a =line-prefix=
  gutter, and its body highlighted in *its own language* through [[*Highlighting a string][=highlight=]].
- **A table is aligned** under a rule, with the rows above the first =|---+---|=
  set bold and no vertical rules at all — the printed convention.
- **A quote block** gets a bar and the comment face; a heading's =:tags:= come off;
  =-----= becomes a rule.
- **The buffer is read-only for real**, through =set-buffer-read-only=. See
  [[*Read-only, and writing anyway][Read-only, and writing anyway]]: a program may still write to it, which is what
  lets a frozen curriculum receive a transcribed answer.

The policy is six =defparameter=s and one =case=. =%org-frozen-block= is the
extension point — it answers the overlay plist a =#+begin_NAME= body wants, so
giving a kind of block a new look is a line in its arm.

Reveal-on-cursor is switched off through a list org-modern owns:

#+begin_src lisp
(pushnew "my-reader-mode" *org-modern-appear-inhibit-modes* :test #'string=)
#+end_src

* A curriculum

| Form                                 |   | Answers                                       |
|--------------------------------------+---+-----------------------------------------------|
| =(math-curriculum-p)=                  | R | =T= when this buffer declares itself one.       |
| =(math-units)=                         | R | =(:id :title :begin :end)= per unit, in order.  |
| =(math-unit-at-point)=                 | R | One of those, or =NIL=.                         |
| =(math-problems &optional unit)=       | R | Problem plists, in order.                     |
| =(math-problem-at-point)=              | R | One problem plist, or =NIL=.                    |

| =(math-src-block problem)=             | R | =(:lang :tangle :body :begin :end)=, or =NIL=.    |

A whole maths course as one org file — units, problems, and somewhere for your
answers to land — all of it ordinary org with =#+ZEMACS_*= properties on the
headings. The format is specified in [[file:curriculum.org][curriculum.org]], precisely enough to hand to
a model as "generate one of these"; the reader is =runtime/modes/math.lisp=.

Two things to know before writing against it. A plist is a *reading*, not a
handle: it describes the buffer as it was, so both writers re-read before they
write and use the plist only to say which problem was meant. And both writers are
a single =replace-region=, for the reason [[file:threading.org][threading.org]] gives — a =delete-region=
followed by an =insert= can take a keystroke between them, and a half-written
property drawer is a corrupted document. =math-response-insert= is idempotent as
well as atomic.

*Nothing here decides a status.* =:ZEMACS_STATUS:= is =todo= or =done= and the
learner sets it; there is no checker and no answer key anywhere in the format.

* The region

#+begin_src lisp
(defun comment-block ()
  "Prefix every line of a block selection with `;; '."
  (dolist (r (reverse (region-ranges)))

** Read-only, and writing anyway

There are two reasons a buffer refuses an edit and =buffer-read-only-p= tells them
apart, because they are not the same fact:

- =:generated= — the dashboard, magit, dired, a terminal. There is no document
  behind it; the text is a rendering of state and the next refresh would throw
  an edit away. Nothing can make one of these writable, and nothing should.
- =:claimed= — an ordinary file buffer whose *mode* has decided you are reading
  rather than writing. =org-frozen-mode= is the first; =set-buffer-read-only= is
  how a mode says it, on entry, and takes it back in its exit hook.

The refusal is one line in =Editor::apply=, tested against "does this command
mutate the document" — so it covers a keystroke, an =:s= substitution, a paste and
an =insert= from Lisp alike, and a new command cannot accidentally get past it.
The cursor still moves, search still works, folds still fold: read-only is not
the same as disabled.

Which means Lisp needs a way through, and =with-inhibited-read-only= is it —
Emacs' =inhibit-read-only=, with the one difference that it lifts a =:claimed= flag
and never a =:generated= kind:

#+begin_src lisp
;; A frozen curriculum is still the buffer a transcribed answer lands in.
(with-inhibited-read-only
  (replace-region beg end transcription))
#+end_src

=UNWIND-PROTECT=, so a body that throws still leaves the document frozen. Note the
window: the flag lives on the editor behind a mutex that is released between
primitives, so a keystroke arriving while =body= runs sees the buffer unfrozen.
Keep =body= short — a =replace-region= or two, which is what it is for.

#+begin_src lisp
(buffer-names)                     ; => ("main.rs" "*dashboard*" "*scratch*")
(buffer-info)
;; => (("main.rs" "/src/main.rs" T "rust-mode")
;;     ("*dashboard*" NIL NIL "fundamental-mode")
;;     ("*scratch*" NIL NIL "fundamental-mode"))

(defun modified-buffers ()
  "Report which buffers have unsaved changes."
  (let ((dirty (remove-if-not #'third (buffer-info))))
    (message (if dirty
                 (format nil "unsaved: ~{~a~^, ~}" (mapcar #'first dirty))
                 "everything saved"))))
#+end_src

=with-current-buffer= genuinely *shows* the other buffer while the body runs —
zemacs has one live buffer, and switching is the only way to reach another one's
text. Keep the body short, and prefer it for reading:

#+begin_src lisp
(with-current-buffer "*scratch*" (buffer-string))
#+end_src

Two buffers with the same base name are indistinguishable to it, and the first
one wins.

** Buffers with no file behind them

=create-buffer= is what =*Messages*=, an =*xref*= listing and any other generated
view are made of. Three things about it:

- it is *idempotent by name* — a second call shows the buffer rather than
  stacking a copy nobody can tell from the first, so a command that fills a
  buffer is written as "make it, then write into it";
- it is applied *on the spot*, unlike =find-file=, which lands a frame later. The
  very next form is already in the new buffer. That is the whole reason the
  =*Messages*= command below is five lines;
- what it makes is an *ordinary* buffer — writable, no path, and never saved
  unless you give =save-file= somewhere to put it. It is =*scratch*=, not
  =*magit*=: the generated buffers (dashboard, magit, dired, terminal) are
  read-only views the editor re-renders, and Lisp does not make those.

#+begin_src lisp
(defun messages-buffer ()
  "Show the message log in a buffer, newest at the bottom."
  (let ((log (messages)))
    (create-buffer "*Messages*")
    (replace-region 0 (point-max) (format nil "~{~a~%~}" log))
    (goto-char (point-max))))
#+end_src

=language= is the tree-sitter language id (="rust"=, ="lisp"=, ="python"=), not a
mode name — a mode is what Lisp dispatches on and a language is what gets
coloured, and a buffer can want one without the other. =set-language= changes it
afterwards.

=kill-buffer= refuses the last remaining buffer and says so; every window showing
the killed buffer, in any frame, moves to the live one. It never asks, whatever
=(buffer-modified-p)= says — confirming is policy, policy is Lisp's, and the
reader is right there.

* Keys and commands

| Form                             |   | Effect                                                |
|----------------------------------+---+-------------------------------------------------------|
| =(define-key mode keys command)=   | P | Bind =keys= to =command= in =mode=.                          |
| =(key-bindings)=                   | R | Every binding as =(MODE KEYS COMMAND)=, sorted.          |
| =(where-is command)=               | H | Just the bindings for one command.                    |
| =(register-command name)=          | P | Offer =name= in =M-x=.                                    |
| =(clear-commands)=                 | P | Empty the =M-x= list — call it before republishing.     |
| =(command-list)=                   | R | What =M-x= currently offers.                             |
| =(call-command name)=              | H | *Run* a command by name — the same resolution a key binding does. |
| =(term-send-key key)=              | H | Send one keystroke to the shell. Dropped if none is running. |

=call-command= is the other half of =define-key=: it resolves =name= exactly as
pressing the key would, so a built-in verb runs as a verb and anything else is
called as =(name)= in the image. =(call-command "magit-status")= and a key bound to
="magit-status"= cannot drift apart, because they are the same line of code.

=term-send-key= takes a key spelled the way =(key-bindings)= reports one — ="a"=,
="SPC"=, ="C-c"=, ="<esc>"=, ="M-<bs>"= — so the string read out of a binding is the
string that can be sent. One token, never a sequence; an unspellable one reports.

** =mode=

Either a *modal state* — ="normal"= ="insert"= ="visual"= ="visual-line"=
="visual-block"= ="dashboard"= ="magit"= ="dired"= ="terminal"= (with the aliases
="vline"=, ="vblock"=, ="git"=, ="term"=) — or *any other string*, which is taken to
name a major or minor mode and applies only in its buffers.

That is one primitive covering both: =(define-key "org-mode" "SPC m b" "org-bold")=
needs nothing new. An unknown mode name is not an error, since a binding may be
made long before the mode it belongs to is entered.

** =keys=

Space-separated tokens. A token is a literal character, =SPC=, a modifier chord,
or a bracketed name:

: a  A  1  SPC  -  +
: C-x  M-o  C-M-j
: <ret>  <tab>  <bs>  <esc>  <left>  <right>  <up>  <down>
: C-<ret>  C-M-<ret>  M-<bs>

Spacing is normalised, so ="gd"= and ="g d"= are the same sequence. A single
unseparated token containing =-= or starting with =<= is left alone, which is why
=<tab>= is one key and not five. An unseparated *mix* like ="g<tab>"= is not
supported — write ="g <tab>"=.

** =command=

The same namespace as a dashboard action. It is a *built-in verb* if it names
one, otherwise it is called as the Lisp form =(command)= — with no arguments,
which is why a command is a zero-argument function.

Built-in verbs, resolved by the editor before the image is asked:

| Verb                                        | What it does                         |
|---------------------------------------------+--------------------------------------|
| =quit=                                        | Quit.                                |
| =find-file=                                   | Open the file prompt.                |
| =execute-command= / =M-x=                       | Open the command prompt.             |
| =switch-buffer=                               | Open the buffer prompt.              |
| =search-line= / =consult-line= / =goto-line=      | Pick a line by fuzzy match.          |
| =search-project= / =consult-ripgrep= / =grep=     | Ripgrep across the project.          |
| =split-window-right= / =split-window-below=     | Split.                               |
| =delete-window= / =other-window= / =ace-window=   | Windows.                             |
| =new-frame= / =delete-frame=                    | Frames.                              |
| =eval-buffer= / =eval-region= / =eval-last-sexp=  | Evaluate live buffer text.           |
| =eval-dwim=                                   | Selection, else the form under point, else the buffer. |
| =magit-*=                                     | A git verb.                          |
| =dired= / =dired-*=                             | A dired verb.                        |
| =terminal= / =term= / =shell= / =terminal-*=        | A terminal session — see below.      |
| =ai=                                          | Pick a coding agent. =C-a=.            |
| =config=                                      | Open the init file.                  |
| =open:PATH=                                   | Open a specific path (=~/= expanded).  |
| =scratch=                                     | Leave the dashboard.                 |
| =<something>-mode=                            | Set the major mode, unless a Lisp command of that name is registered. |

Anything else is =(that-name)= in the image.

The precedence when a key is pressed is: bindings for the buffer's *minor* modes
(most recently enabled first), then its *major* mode, then the current modal
state's map, then the built-in vim grammar. So config always wins, and a
mode-local binding wins over a global one.

That holds for a mode-local *sequence* too: while one is still being typed, an
exactly matching global binding does not fire. =C-c= is bound everywhere to
=eval-dwim=, and =(define-key "lisp-mode" "C-c C-e" ...)= is what makes =C-c= a
prefix in Lisp buffers and nowhere else. Without it the global binding would
fire on the first key and the sequence could never be reached.

While a sequence is pending the editor calls =(which-key KEYS)= in the image, if
something has defined it — that is the whole hook =runtime/modes/which-key.lisp=
hangs from, and a config that does not define =which-key= never notices.

What it answers with can go two places. =(message ...)= is the status line;
=(which-key-row "KEY LABEL")= appends one row to the *panel* the renderer draws
in a grid above the status line, and =(which-key-row)= with no argument empties
it. Rows go one at a time for the same reason completion candidates do — the
write envelope carries a single string — and the renderer splits each at its
first space, which a normalised key token never contains.

Nothing has to retire the panel: the editor empties it itself the moment no key
sequence is pending, so a binding that fired, an =Esc=, and a key that turned out
not to be a prefix all clear it without Lisp being called at all. And it is not a
prompt, deliberately — a prompt would swallow the next keystroke, which is the
one which-key exists to help you aim.

#+begin_src lisp
(where-is "find-file")
;; => (("normal" "SPC f f" "find-file") ...)  — one row per mode it is bound in

(defun describe-mode-keys ()
  "Every binding that applies in this buffer's major mode."
  (let ((mode (major-mode)))
    (message (format nil "~{~a~^  ~}"
                     (mapcar #'second
                             (remove-if-not (lambda (b) (string= (first b) mode))
                                            (key-bindings)))))))
#+end_src

*Note the collisions.* =goto-line=, =dired= and =terminal= are built-in verbs *and*
Lisp functions here. A key bound to the string reaches the verb; the Lisp
function is what Lisp calls. They do compatible things — the verb prompts, the
function takes an argument — which is the same split Emacs has.

* Prompts

| Form                                       |   | Effect                            |
|--------------------------------------------+---+-----------------------------------|

** The editor's own pickers

=kind= is one of ="file"=, ="buffer"=, ="command"= (=M-x=), ="line"= (=consult-line=),
="grep"= (ripgrep), ="project-file"=, ="ex"= (=:=) or ="search"= (=/=). Unknown names

#+begin_src lisp
(defun find-file-here ()

  (open-prompt "file"))
#+end_src

*What the answer does is fixed by the kind* — a file is opened, a command is run,
a line is jumped to. So this is "put one of the editor's pickers up", and the
next section is the other thing.

** Asking your own question

=read-string= and =completing-read= are what most interactive commands are built
out of. Both answer the prompt id and *return before the user has typed
anything*, so there is no value for them to return: the answer arrives at
=callback=, on a later turn of the Lisp queue.

#+begin_src lisp
(defun rename-thing ()
  (read-string "New name: "
    (lambda (name)
      (when name                       ; NIL means the user backed out
        (replace-region (point) (+ (point) 4) name)))))

(defun switch-project-buffer ()
  (completing-read "Buffer: " (buffer-names)
    (lambda (pick) (when pick (switch-to-buffer pick)))))
#+end_src

- =callback= is called with the string typed, or with =NIL= if the prompt was
  cancelled — Escape, =C-g=, or backspacing past the start. It is *always*
  called exactly once, so a command can clean up in it.
- Nothing is required to match. With no candidate highlighted the answer is what
  was typed, which is Emacs' =require-match= =NIL= and the useful default.
- =candidates= is a list of strings, matched by the same fuzzy matcher every
  other picker uses, and offered in the order you gave.
- Errors signalled inside =callback= cost you that one answer and report
  =prompt handler error: ...=. They never reach the editor.

*** Why it is a continuation and not a return value

Because the Lisp thread evaluates one queued form at a time. A primitive that
*waited* for a keystroke would stop the image — every mode hook, every key bound
to a Lisp command, every =M-x= — until the question was answered. That is exactly
the elisp behaviour [[file:threading.org][threading.org]] exists to avoid, and it is the same trade
=rpc-request= makes for the same reason.

The route is the one a JSON-RPC reply already takes, deliberately rather than as
a second mechanism:

1. the closure is parked in =*prompt-continuations*= under a fresh id;
2. that id goes into core, which opens a prompt whose destination is *Lisp*
   rather than a file or a command;
3. accepting or cancelling it makes the editor call =(%prompt-reply ID ANSWER)=
   in the image — the same route a mode hook takes;
4. =%prompt-reply= looks the id up and calls the closure.

No foreign thread ever calls into ECL and nothing blocks the editor. The cost is
that *your callback cannot return a value to whoever asked*: put the rest of the
command inside it, or chain a second prompt from within the first.

Opening one prompt from inside another's callback is fine. Opening a *second*
prompt while the first is still up is not — the first continuation never gets a
reply and stays in the table. =(clrhash *prompt-continuations*)= is the sweep.

** Terminal sessions come in more than one

There is a live child per terminal *buffer*, not one per editor, and the buffer
is how everything addresses it — keystrokes reach the session whose buffer is
live, and the rest keep running. See the buffer-kind table in [[file:model.org][model.org]].

| Verb                    | What it does                                                  |
|-------------------------+---------------------------------------------------------------|
| ="open"=                  | Show the shell session, starting it if there is none.          |
| ="new"=                   | A *second* shell, however many are already up.                 |
| ="run:NAME:COMMAND"=      | Run =COMMAND= in a buffer called =*NAME*=. What AI mode is built on. |
| ="rerun:NAME:COMMAND"=    | The same, but *replacing* a session already called =*NAME*= instead of opening a second. For a program you run over and over; =run:= is for a harness you start. |
| ="close"=                 | Hang up on the live session and kill its buffer.               |
| ="restart"=               | Run the same command again in the *same* buffer.               |
| ="next"= / ="prev"=         | Walk the sessions, wrapping.                                   |
| ="normal"= / ="insert"=     | Out to the scrollback and back in. =C-M-t= both ways.            |

=run:NAME:COMMAND= is the one verb carrying an argument. =COMMAND= is split on
whitespace, so an argument containing a space cannot be expressed — that is a
named ceiling, not an oversight, and the upgrade is the verb carrying a list.
The command must be on =$PATH=: an absent one is reported by name and no buffer
is opened, rather than a PTY appearing and dying.

#+begin_src lisp
(terminal "run:notes:hx ~/notes.md")          ; anything, not only agents
(call-command "terminal-run:notes:hx ~/notes.md")   ; the same, as a binding
#+end_src

** Files it edits

An agent writing files is the whole point, so auto-revert watches *every* open
buffer four times a second rather than the live one every five seconds. A buffer
with unsaved changes is never clobbered — it gets one message and keeps its
text — and the comparison is on content, so saving a file does not revert the
buffer that saved it.

* Undo, the register and the clipboard

| Form                                      |   | Effect                                |
|-------------------------------------------+---+---------------------------------------|
| =(undo)= / =(redo)=                           | H | One step through this buffer's history. |
| =(copy-region beg end &optional linewise)=  | H | Copy into the unnamed register — what =p= pastes. |
| =(set-register text &optional linewise)=    | H | Put literal text there.               |
| =(register)=                                | R | =(TEXT . LINEWISE-P)=, or =NIL= when it is empty. |

=linewise= is vim's distinction: a linewise register pastes as whole lines above
or below the current one rather than into it.

** The register is the system clipboard

=select-enable-clipboard t= is what the config asks for, so there is no separate
kill ring: the unnamed register and the system clipboard are mirrored. =yy= here
is pasteable in a browser, and =⌘C= there is what the next =p= puts back — and
=(register)= therefore reads whatever was copied *anywhere*, not only what this
editor yanked.

The mirror is in the app layer, because core cannot reach the window system:
pushed once a frame off a revision counter, pulled on the window system's own
"the clipboard changed" event rather than by polling it. Text arriving from
outside is treated as linewise only if it ends in a newline — which is what =yy=
would have produced, and the best a bare string can be asked.

Named registers (=""ayy"=) are vim-side only and are *not* mirrored; the =+= and
=*= registers do not exist as separate registers, because with this setting they
would be aliases for the one that already is the clipboard.

* Subprocesses and JSON-RPC

A long-lived child, spoken to in JSON-RPC 2.0 over its stdin and stdout. Rust
owns the pipe — spawning, =Content-Length= framing, id allocation, draining the
child's stderr, noticing it die — and *nothing else*. Which request to send and
what to do with the reply is Lisp, in =runtime/rpc.lisp=.

This is a different thing from =(terminal "open")=: a PTY is a screen a program
draws on, and this is a pipe you ask questions down.

Load it before use — the shipped =init.lisp= does:

#+begin_src lisp
(load (merge-pathnames "rpc.lisp" *runtime-dir*))
#+end_src

| Form                                                |   | Answers                                                     |
|-----------------------------------------------------+---+-------------------------------------------------------------|
| =(rpc-start program &key args cwd name on-notify on-request on-exit)= | H | A connection handle, or =NIL= if the program could not be started. |
| =(rpc-request conn method params callback)=           | H | The request id. =callback= is called with =(RESULT ERROR)= later. |
| =(rpc-notify conn method &optional params)=           | H | =T= when it went out.                                         |
| =(rpc-respond conn id result &optional error)=        | H | Answer a request the *child* made.                            |
| =(rpc-stop conn)=                                     | H | Hang up. Queued messages are written first.                 |
| =(rpc-live-p conn)=                                   | H | =T= while the child is running.                               |
| =(rpc-connections)=                                   | H | =((CONN NAME) ...)=                                           |

** The handlers

All three run on the Lisp thread, later, and take the connection first:

: (on-notify  CONN METHOD PARAMS)
: (on-request CONN ID METHOD PARAMS)     ; must answer with rpc-respond
: (on-exit    CONN REPORT)               ; REPORT carries the child's last stderr

A request with no =on-request= is answered =-32601= automatically, because
JSON-RPC insists a request be answered even to refuse it — a server left waiting
on one sits there forever.

** How a reply reaches Lisp

=rpc-request= returns *before the child has been asked*, so there is no value for
it to return. What happens instead:

1. a reader thread in Rust parses the frame and pushes it onto a channel;
2. the main thread drains that channel once a frame, turns the JSON into a Lisp
   form, and queues =(%rpc-event CONN KIND FORM)= for the Lisp thread — the same
   route a mode hook takes;
3. =%rpc-event= looks the id up in the connection's pending table and calls the
   closure parked under it.

No foreign thread ever calls into ECL and nothing blocks the editor, which is
the contract in [[file:threading.org][threading.org]]. The cost is that *your callback runs later, on a
turn of the Lisp queue of its own*: it cannot return a value to whoever asked,
so write it as a continuation.

** JSON

Decoding is Rust's; a message arrives already =READ=:

| JSON      | Lisp           | JSON       | Lisp                    |
|-----------+----------------+------------+-------------------------|
| =null=      | =NIL=            | =[a, b]=     | =(a b)=                   |
| =true=      | =T=              | ={"k": v}=   | =(("k" . v))= — an alist  |
| =false=     | =NIL=            | number     | integer or double       |

Encoding is Lisp's, because building a request *is* protocol:

| Form                        |   | Answers                                              |
|-----------------------------+---+------------------------------------------------------|
| =(json-encode x)=             | H | JSON text. =NIL= → =null=, =T= → =true=, =:false= → =false=, =:empty-object= → ={}=, =:empty-array= → =[]=. |
| =(json-string s)=             | P | =s= as a JSON string literal, quotes and escapes included. |
| =(jobj "k" v ...)=            | H | An object from alternating keys and values.          |
| =(jarr a b ...)=              | H | An array.                                            |
| =(jget object &rest keys)=    | H | Walk a decoded object. =NIL= for anything not there — never signals. |

#+begin_src lisp
(json-encode (jobj "position" (jobj "line" 3 "character" 0)))
; => {"position":{"line":3,"character":0}}

(jget msg "params" "range" "start" "line")   ; => 3, or NIL
#+end_src

*Three things arrive as =NIL=* — =false=, =null= and an empty array or object — so a
reader cannot tell "absent" from "explicitly false". Nothing in LSP depends on
the difference; the upgrade is =:false= / =:null= keywords in the decoder.

*Whether a list encodes as an object or an array is inferred*: a list whose first
element is a cons with an atom in its car is an alist. =jobj= and =jarr= make that
unambiguous, and hand-written literals mostly do too — =((1 2) (3 4))= is the
shape that gets it wrong.

| =(lsp-status)=                      | H | What is running, and where.                               |

** =after-change-hook=

The one event the editor reports about the *document*, and what drives document
synchronisation. It is called with no arguments whenever the live buffer's
revision moves — every keystroke in a buffer being edited, and once when a file
is opened. =*after-change-functions*= is the list it runs, so this file and your
config can both hang something off it.

#+begin_src lisp
(push (lambda () (when (> (point-max) 100000) (message "big file")))
      *after-change-functions*)
#+end_src

It carries no *delta*, which is why =textDocument/didChange= sends the whole
buffer. See the ceiling in [[file:boundary.org][boundary.org]].

** =point-moved-hook=

The other event, and its twin: the *cursor* moved. Called with no arguments
whenever the live buffer's point offset changes — a motion, a click, a jump, an
edit that shifted it, or a switch to a buffer whose point is elsewhere.
=*point-moved-functions*= is the list it runs, and =runtime/modes/modes.lisp= is
where both are declared.

This is what a mode hangs *live editing* off. =org-modern-appear= is the shipped
example: it reveals the markup the cursor is inside, and before this hook existed
it could only do so when you typed, because the change hook is the only other
thing the editor says. So the asterisks around a word appeared as you edited it
and stayed hidden as you walked onto it.

#+begin_src lisp
(push (lambda () (message (format nil "col ~d" (column))))
      *point-moved-functions*)
#+end_src

It fires at most once per keystroke, in every buffer, so a function on it gets
the same budget the change hook has: a constant amount of work, or a cheap test
that decides whether to do any. A buffer rescan here is felt. It carries no
*previous* position either — a config that wants to act on the range you left
has to remember it, which is what =org-latex-maybe-preview= in =init.lisp= does
with one integer.

* The escape hatch

Both halves of the bridge are one C entry point each, and both are exported. If
a name is missing but the underlying reader or verb exists, call them directly.

** =(%query name a b)=

Answers =name= with up to two integer arguments. Rust answers with a *string of
Lisp source* and the shim =READ=s it, which is how one C signature returns
integers, strings, =NIL=, conses and lists alike. An unknown name answers =NIL=.

Its ceiling is arguments: two integers, no strings. Anything needing a string
argument is a command.

** =(%do verb arg a b)=

Issues the command named by =verb=, with an optional string and up to two
integers. =NIL= for =arg= means absent. An unknown verb reports =no such command:
...= in the status line.

| Verb                                       | =arg=   | =a=          | =b=   |
|--------------------------------------------+-------+------------+-----|
| ="undo"= ="redo"=                              | —     | —          | —   |
| ="switch-buffer"=                            | —     | index      | —   |
| ="split-window-right"= ="split-window-below"=  | —     | —          | —   |
| ="delete-window"= ="other-window"=             | —     | —          | —   |
| ="select-window"=                            | —     | window id  | —   |
| ="new-frame"= ="delete-frame"=                 | —     | —          | —   |
| ="select-frame"=                             | —     | frame index | —  |
| ="scroll"=                                   | —     | lines, signed | — |
| ="yank"= / ="yank-lines"=                      | —     | beg        | end |
| ="set-register"=                             | text  | linewise?  | —   |
| ="paste"=                                    | —     | after?     | —   |
| ="git"= ="dired"= ="term"=                      | verb  | —          | —   |
| ="open-at"=                                  | =path:line:text= | —  | —   |

| ="kill-buffer"=                              | —     | index      | —   |

="call"= is the one verb that is not a single command: it resolves a name the way
a key binding does and issues whatever *batch* that produces, which is why it is

one-line =DEFUN= in =shim.c= — nothing in C. Adding a reader is one arm of the
=match= in =zemacs_core::query= plus a name in the list in =QUERIES_FORM=.

** The subprocess primitives

Five, and none of them knows what a protocol is. =runtime/rpc.lisp= is written on
top of exactly these; anything it can do, you can do.

| Form                                          | Answers                                       |
|-----------------------------------------------+-----------------------------------------------|
| =(%rpc-start program args-json cwd)=            | A connection handle, or 0. =args-json= is a JSON array of strings, or ="". |
| =(%rpc-send conn method params-json reply-p)=   | The request id, or 0 for a notification. =params-json= =NIL= sends no params at all. |
| =(%rpc-respond conn id-json result-json error-json)= | =NIL=. The id is raw JSON because JSON-RPC allows a string there. |
| =(%rpc-stop conn)=                              | =NIL=.                                          |
| =(%json-quote text)=                            | =text= as a JSON string literal.                |

Three of them hand a value back, which is what earns them C entry points rather
than =%do= verbs; the other two carry more strings than =%do='s single one.

Malformed JSON is *refused* rather than written: a half-written message would
desynchronise the child for the rest of the session, and the symptom would
surface three requests later. The refusal is a line in the status line.

* Redefinition, and advice

This is Common Lisp, so there is no advice framework and none is needed:
=fdefinition= is the mechanism.

#+begin_src lisp
;; Log every font-size change, and still make it.
(let ((old (fdefinition 'set-font-size)))
  (setf (fdefinition 'set-font-size)
        (lambda (n)
          (message (format nil "font size -> ~a" n))
          (funcall old n))))
#+end_src

That is not a curiosity: =runtime/modes/modes.lisp= makes global settings revert
when a mode is left by wrapping each setting primitive exactly this way, because
there was no reader to compare against. Capture the old definition in a =LET= and
guard against re-wrapping on a config reload — wrapping a wrapper recurses until
the stack runs out. =DEFVAR= (not =DEFPARAMETER=) is the usual guard, since a
reload must not re-capture.

*A built-in verb cannot be advised.* Core resolves the names in
=BUILTIN_COMMANDS= (=crates/core/src/evil.rs=) before it ever asks the image, so
redefining a Lisp =quit=, =find-file= or =delete-window= changes nothing that a key
binding, a dashboard item or =M-x= does. Names that are *not* in that list —
=save-file= among them — fall through to the image and are advisable.
